# 项目开发规则

## 定位

本文件记录长期有效的项目组织和开发约束，不记录临时任务。

## 当前优先级

开发依次服务：

1. 标的身份标准化。
2. 行情、财务、公告、基金和研报数据。
3. 估值、质量、成长、收益、风险、技术指标和图表。
4. 行业、市场、基准和同行比较。
5. 可解释策略、时间尺度与回测。
6. 标的发现。
7. Agent IDE 研究指引。

基础设施不得因为容易实现而取代研究能力。Web、鉴权、自动通知和部署只有在用户明确提出新阶段时推进。

## 文档

- `README.md`：项目用途、安装和使用。
- `report/`：面向用户的研究报告、图表和同源数据产物。
- `docs/long_term/`：长期路线与技术债。
- `docs/modules/`：模块职责、边界、输入输出和依赖。
- `docs/` 根目录：短期计划、阶段状态和跨模块协调。
- `.agent/docs/`：Agent 按场景读取的长期规则。

用户报告不得写入 `docs/`；开发文档不得散落到 `src/`、`data/`、`logs/`、`references/` 或 `temp/`。

## 代码与测试

- 源码和可执行逻辑写入 `src/<module>/`。
- 单元测试写入 `src/tests/<module>/unit_tests/`。
- smoke 写入 `src/tests/<module>/smoke_tests/`。
- 跨模块测试入口使用 `src/tests/run_all_unit_tests.py`。
- 不重新建立 `src/unit_tests/` 或 `src/smoke_tests/`。
- 共享基础设施可以拥有独立目录，不强塞进业务模块。

### 测试资产增长约束

1. 新测试必须保护独立的业务语义、边界、失败模式或外部契约；不得只验证枚举成员、固定注册数量、容器行为或实现调用次数。
2. 同一公共流程只保留一个主 smoke；Provider、标的或参数差异优先参数化，不复制整套脚本。
3. 新正式执行链路覆盖旧 smoke 后，同一变更中删除或降级旧入口，不长期并行维护。
4. 默认单元测试不得联网；真实源验证只作为按需 smoke，失败必须区分远程不可用与业务无数据。
5. 跨模块验收脚本只负责编排和关键断言；可由单元测试覆盖的计算细节不得继续堆入验收脚本。
6. 修复缺陷时优先补能稳定复现该缺陷的回归测试；新增功能不要求机械增加测试数量。

## 数据

- 本地 SQLite、查询缓存和用户数据写入 `data/database/`。
- 可共享、低频、Git 友好的快照写入 `data/daily_data/`。
- `daily_data` 不使用 SQLite 作为 Git 增量格式。
- 交互式补取默认写 SQLite，只有用户明确要求且质量检查完成后才发布到 `daily_data`。
- 自动跟踪集合只能物化去重后的资产身份，不得泄露用户、持仓数量、标签和关注理由。
- 定时任务必须先完成跟踪集合、来源验证、关联、去重、质量门禁和失败隔离；此前只允许手动运行。

## 用户空间

- 当前用户隔离用于正常使用中的数据归属，不是安全多租户。
- 用户数据必须经过稳定 `user_id` 和明确服务/repository 边界。
- 当前不得预建密码、角色、ACL、行级安全或每用户独立数据库。
- 只有用户提出新安全目标后才升级认证和授权。

## 其他目录

- 日志写入 `logs/`。
- 外部项目和资料写入 `references/`，默认只读。
- 一次性中间产物写入 `temp/`，不得作为长期事实来源。

## 协作与版本

1. 保护用户已有改动，不回滚无关内容。
2. 猜测必须标注；影响未来行为的歧义先确认。
3. 未定版阶段优先修正设计，不为旧格式增加兼容层；项目自有计算、策略、分类、报告和研究元数据版本暂时统一使用 `v1`，修正直接覆盖 `v1`，不得递增为 `v2`、`v3`。
4. 第三方 API 路径、依赖版本不属于项目版本；SQLite `SCHEMA_VERSION` 是内部迁移序号，也不得包装成产品或研究能力版本。
5. 生产规范、milestone 或正式版确立后再讨论兼容和项目版本递增。
6. 任何长期规则变更先修改本文件，再同步入口和说明。
7. 版本、schema 序号、digest 和计算追溯字段属于 Agent/开发者内部信息；用户报告、用户界面和面向用户的结论默认不展示，除非用户明确询问。

## 研究代码额外要求

1. 每个策略、指标和结论声明时间尺度。
2. 正式代码不得依赖 `references/` 运行环境。
3. 数据不足时停止，不得用 prompt 或 fixture 填补底层能力。
4. 新策略编码前必须先检索可审阅的开源实现和公开研究；记录 URL、许可证、原始机制、可复用部分和不采用部分。
5. 没有完成来源登记和机制对照的策略不得进入正式实现。项目可以改写或组合机制，但不得把未检索的自创规则包装成已有验证基础的策略。
6. 策略验证不得用任意固定样本数作为通用准入门槛。应按问题选择连续信号分层、滚动样本外、时间序列分块、自助法、跨标的面板或事件阶段分析，并明确相关性和重叠窗口处理。
