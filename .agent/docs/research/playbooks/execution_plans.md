# 执行计划与全局日历

## 登记与修订

1. 研究结论中产生时间节点、持续观察或应对动作时，先看 `plan-register --help`，把承诺拆成有完成标准的节点，通过公共命令登记，不只留在报告或对话里。
2. 用户尚未确认执行承诺时登记草稿；用户确认后，沿用登记键修订激活。引用原报告、辩论、观点或动作，不复制出另一份研究结论。旧报告不批量自动激活。
3. 登记后用 `plan-show --user-id <id> --plan-id <id>` 核对完整计划，再用 `calendar --user-id <id> --through <日期>` 核对全局安排。告诉用户计划已登记，不把尚未登记的文字安排说成系统已跟踪。
4. 条件、仓位或执行安排改变时，先 `plan-show`，再按 `plan-register --help` 修订；按输出处理冲突，不盲目覆盖。有过处理历史的节点改条件时用新节点，取消旧安排而不改写历史。

## 巡检与处理

1. 用户要求查看本日、未来或逾期待办时先看 `calendar --help`，运行 `calendar --user-id <id>`；需要同时研究与结算时运行 `routine --user-id <id>`，看 `steps.calendar` 及 `next_actions`。
2. 按输出读取完整计划和当前修订，核实当时证据、任务条件、依赖及完成标准。行动前使用最新持仓、现金和组合约束核查跨计划冲突；不因任务到期自动交易。
3. 按 `task-resolve --help` 记录每次处理的结论、证据与后续时间。证据不足不得写成条件不成立；研究建议不得当作成交，实际执行需成交或用户明确确认依据。
4. 用户报告实际交易后按原流程记录成交/持仓，再更新该执行节点。只完成本期检查，不关闭未来周期节点。

## 回顾

1. 先看 `plan-review --help`，按编号回看计划、修订、延期、阻塞和执行证据；历史重放按帮助设置当时的信息截止时间。
2. 判断是否成立另走 `settle-ledger`、`decision-review`，辩论观点走 `debate --action scorecard`；不把任务完成率解释为判断正确率。
