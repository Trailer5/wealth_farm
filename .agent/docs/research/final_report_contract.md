# 最终决策研究报告契约

## 角色

最终报告是 Agent 在基础包和多轮探索完成后形成的用户决策文档。它引用基础研究包，不复制全部内部数据；基础包、smoke 输出和自动验收报告都不能直接改名充当最终报告。

完整成果保存为 `report/` 下的普通 Markdown，静态图使用相对路径引用 `report/assets/`。文件名必须与“基础研究包”明确区分。

## 必需章节

1. **决策摘要**
   - 截止日期、当前结论和置信边界；
   - 是否购买、何时行动、购买多少的直接答案；
   - 不可回答时直接写明原因。
2. **用户目标与适用边界**
   - 持有期限、持仓状态、组合角色、风险与流动性约束；
   - 未提供的用户信息及其影响。
3. **标的与核心论文**
   - 标的是什么、收益来源、风险暴露以及论文成立条件。
4. **是否值得买**
   - 当前定价隐含预期、主要下行、合理替代方案和机会成本。
5. **何时行动**
   - 当前状态、可观察进入/等待/放弃条件、分批规则和信号有效期。
6. **购买多少**
   - 当前权重、目标区间、风险预算、压力损失和绑定约束；
   - 不可计算时列出所缺输入，不给假定比例。
7. **三情景**
   - 乐观、基准、悲观情景的关键假设、观察变量和决策影响；
   - 没有模型依据时不写精确概率。
8. **最强反方**
   - 最可能推翻主论文的解释、已有反证以及当前为何仍接受或否定论文。
9. **失效、退出与复查**
   - 论文失效、风险触发、减仓/退出条件和下次复查节点；
   - 可机器观察与需人工复查的条件分开。
10. **关键证据与未知**
    - 核心来源、发布日期、链接、页码或项目派生方法；
    - 仍可能改变结论的未知项。

## 三类决策输出

- 是否购买必须是考虑、观察、回避、持仓复核或证据不足之一。
- 时点必须是行动、分批、等待、不适用或证据不足之一。
- 仓位必须是可计算区间、需要用户上下文或当前能力不支持之一。

面向用户使用自然语言，不直接展示内部枚举、ID、digest、schema、源码路径或测试成熟度标签。

仓位章节只消费已验证的 `PositionPlan`：available 时解释当前权重、目标区间、压力损失、真正绑定的约束和与时点条件关联的规划金额；user_context_required 时逐项说明缺失输入及补齐方式；unsupported 时说明 profile 或公共能力边界。不得把区间上限改写成推荐点位，也不得把分批规划改写成订单。

## 证据表达

报告中的陈述必须能区分：

- **事实**：带来源和截止日期；官方、第三方汇总与项目派生不得混写。
- **推断**：说明由哪些事实推得以及限制。
- **假设/情景**：说明验证变量和失效条件。
- **未知**：说明为何重要和怎样补齐。

核心行动结论至少能回溯到基础包或探索证据。外部网页事实优先链接官方原文；文档证据尽量给发布日期和页码。不得把远程失败、业务无数据、近似值或派生值写成官方结论。

每个带证据的事实、推断、情景影响和监测条件必须在正文标出对应证据序号，不能只在文末堆放无关联来源。官方引用必须与探索账本中的 primary 来源及已登记 URL 一致；derived 和 user context 不得由 Agent 改标成官方。仓位装配后新增的 mandate、组合和约束快照引用只能作为用户上下文，最终装配器会按决策简报用户重新加载并复核标的、截止日、币种和估值 digest；价格/风险计算引用仍必须先写入探索账本，只接受对应的 reported 或 derived 来源层级。

## 行动纪律

1. 长期论文、短期时点和仓位预算分别成结论，不合并成总分。
2. 仓位来自用户约束和正式计算；没有输入就正式不可用。
3. 入场条件必须可观察并声明有效期，不预测精确底部。
4. 最强反方和失效条件必须具体到能改变当前动作。
5. 监测规则未经用户确认只作为建议，不自动启用。
6. 报告可以结论为等待、回避或证据不足，不为“完整”强制推荐。

## 发布前复查

发布前逐项确认：

- 基础包存在且身份、截止日期一致；
- 基础 Markdown digest 与 handoff 一致，复用图表、同源数据和 metadata 的 digest 均与 handoff manifest 一致，且 metadata 绑定同一标的和截止日；
- complete/partial/blocked 状态没有被掩盖；
- 三个决策问题均有答案、不适用或正式不可用原因；
- 核心事实有来源，推断可回溯，情景与事实分离；
- 合理替代方案、最强反方、下行和失效条件非空；
- 仓位存在时用户约束和计算输入完整；
- 图表引用为已发布相对静态路径；
- 用户正文没有内部审计字段；
- 会话用户与决策简报一致，发布文件使用隐私安全运行指纹避免跨用户覆盖；
- Markdown 可脱离当前聊天独立阅读。

当前项目已提供 `FinalDecisionResearchReport`、`FinalDecisionReportReviewer` 和 `FinalDecisionReportService`。Agent 必须先把三情景、证据标题/来源/发布日期/可选页码、额外未知和复查日期写入 `FinalReportNarrativeInput`，再调用 `container.final_decision.assemble_and_publish(...)`；只有结构复查、静态产物检查和 Markdown 复查全部通过时才算正式发布。不得绕过该入口直接把自由撰写正文或基础包改名为最终报告。

报告发布后如需本地监测，调用 `container.monitoring.prepare(context, publication, bindings=...)`。该入口会重新加载最终报告服务写入的发布证明，复核用户、workflow、规范化监测计划、文件路径和 Markdown digest；仅有调用方传入的 `review.passed` 或路径不算发布证明。价格、事件和组合权重条件必须由 `MonitoringRuleBinding` 显式给出受支持规则类型及阈值或事件类型；不得从自然语言猜阈值，也不得临时调用内部 Provider。该步骤只保存待确认候选，不注册规则。只有用户明确选择候选后，才调用 `container.monitoring.confirm_and_activate(...)`；人工复查和无法适配条件继续保存在 handoff 中。最终报告内的 `MonitoringPlan` 保持发布时快照和空 `alert_rule_refs`，实际启用状态、规则引用及失败 gap 由 workflow run 与 `MonitoringHandoff` 持有。
