# 项目开发规则

## 定位

本文件记录项目开发的基本规则、项目组织方式和 Agent 协作约束。
本文件记录长期有效的规则。本文件不记录临时想法。
本文件必须使用明确的肯定句和否定句。

## 项目说明

`README.md` 用于介绍项目、说明项目用途、记录安装方法、运行方法和使用方法。
`README.md` 不记录开发过程细节。`README.md` 不记录长期规划、模块内部设计或临时任务清单。

## 文档目录

所有开发文档必须落入 `docs/`。
`docs/long_term/` 记录长期计划、长期路线图和长期技术债。
`docs/modules/` 记录每个模块的要求、边界、能力、输入、输出和依赖。
直接落在 `docs/` 下的文档只记录短期开发计划、当前阶段说明和跨模块临时协调事项。
开发文档不得散落在 `src/`、`data/`、`logs/`、`references/` 或 `temp/` 中。

## 代码与测试目录

代码、脚本和可执行逻辑必须落入 `src/`。
模块代码必须尽量落入自己的主目录，例如数据获取模块使用 `src/data_src/`，主数据与标的身份模块使用 `src/master_data/`。
模块主目录规则必须保留弹性。共享基础设施可以拥有独立目录，例如数据存储、文档处理、通用工具和跨模块运行框架可以不强行归入某一个业务模块。
模块文档必须说明相关目录是模块拥有、模块依赖，还是有限覆盖。
新增测试必须落入 `src/tests/<module>/` 下，并按测试类型继续划分目录。
单元测试必须落入 `src/tests/<module>/unit_tests/`。
smoke 测试必须落入 `src/tests/<module>/smoke_tests/`。
跨模块测试入口和共享测试基础设施可以直接落入 `src/tests/`。
`src/unit_tests/` 和 `src/smoke_tests/` 不得重新建立。
`src/` 不存放长期规划文档。`src/` 不存放业务数据、数据库文件、日志文件、外部项目或临时文件。

## 数据目录

本地数据库文件、SQLite 文件、本地查询缓存和按用户归属的数据必须落入 `data/database/`。
可共享、非用户专属、低频、增量、适合 Git 管理的数据快照必须落入 `data/daily_data/` submodule。
`data/daily_data/` 不得使用 SQLite 二进制文件作为日常 Git 增量格式。它必须优先使用 JSONL、CSV 和 JSON 等可审阅文本格式。
用户交互式补取的数据默认写入 `data/database/`。只有用户明确要求，并且获取、归一化、去重和质量检查全部结束后，才可以主动发布到 `data/daily_data/`。
`daily_data` 自动任务必须以自动跟踪标的集合为输入。该集合必须聚合所有用户的 active 自选、非零持仓、公共自选和人工固定标的，并只输出去重后的标的身份，不得输出用户、关注理由、标签或持仓数量。
易消失、持续新增且需要跨时间积累的新闻、公告、研报元数据、监管信息和来源健康记录是 `daily_data` 定时任务的优先对象。日线行情默认由统一数据访问层按需补取到 SQLite，不得仅因可以定时抓取就设为每日自动任务。
任何定时发布必须先完成跟踪集合同步、数据源验证、标的关联、去重、质量门禁和失败隔离。上述边界未完成时，只允许手动运行，不得启用 schedule。
主仓库的 `data/` 不存放源码。`data/daily_data/` 是独立仓库，可以按其自身规则保存 GitHub Actions 和自动化写入脚本。
`data/` 不存放开发规则。`data/` 不存放临时调试输出。

## 用户空间与数据归属

当前用户隔离只用于让多个用户分别维护自选、持仓、偏好、报告和任务上下文。当前用户隔离不是安全边界。

按用户归属的数据必须包含 `user_id` 或等价用户空间字段。查询和写入必须按当前用户空间筛选，避免不同用户的数据在正常使用中混淆。

自动跟踪标的集合可以读取所有用户空间中的 active 自选和非零持仓，但只能物化标的身份及跟踪来源类型。它不得把 `user_id`、自选列表名称、关注理由、标签、持仓数量或其他用户状态写入共享 `daily_data`。

当前阶段不要求防止用户主动窥探其他用户数据。当前阶段不得为了安全多租户增加复杂鉴权、行级安全、独立数据库、加密隔离或权限系统。

登录或会话如果被 Web UI 需要，只用于识别当前用户空间。项目不得把这种识别表述为严格的隐私隔离或安全多租户。

用户空间必须保留最小安全升级点：使用稳定内部 `user_id`，通过统一用户上下文传递当前用户，并让按用户归属的数据经过明确的服务或 repository 边界。不得把可变用户名直接作为长期主键。

最小升级点不得扩展成当前不需要的安全系统。项目不得预先建设密码体系、角色权限矩阵、资源 ACL、行级安全或每用户独立数据库。

只有用户明确提出新的安全目标或项目进入相应 milestone 后，才可以升级身份认证、授权、审计和租户隔离设计。

## 日志目录

运行日志、调试日志和审计日志必须落入 `logs/`。
`logs/` 不存放业务源码。`logs/` 不存放长期文档。`logs/` 不存放数据库主文件。

## 外部项目目录

外部项目、第三方代码快照、参考仓库和外部资料必须落入 `references/`。
`references/` 中的内容默认只读。Agent 不得修改外部项目内容，除非用户明确要求。
`references/` 不作为本项目源码目录。项目运行代码不得依赖未说明来源和版本的外部快照。

## 临时目录

临时文件、一次性中间产物、实验输出和可删除缓存必须落入 `temp/`。
`temp/` 中的内容不得作为长期事实来源。`temp/` 中的内容不得作为项目必需输入。

## 协作边界

Agent 是项目协作者。Agent 必须保持前后约束一致。
Agent 必须保护用户已有改动。Agent 不得回滚、删除或重写与当前任务无关的内容。
Agent 必须标注不确定事项。Agent 不得把猜测写成事实。

## 版本兼容

用户确立某一版为生产规范、milestone 或正式版之前，项目不需要兼容历史格式和历史接口。
未定版阶段必须优先直接修正设计。未定版阶段不得为了兼容旧方案增加兼容层。

## 一致性要求

新增目录必须符合本文件定义的职责。
新增目录和新增文档必须尽量自解释。命名必须让用户和 Agent 在缺少历史记忆时也能判断用途、归属和边界。
新增文档必须放入正确的文档层级。
新增代码必须放入 `src/`。
新增测试必须落入 `src/tests/<module>/unit_tests/` 或 `src/tests/<module>/smoke_tests/`。
新增本地数据库和按用户归属的数据必须放入 `data/database/`。
新增 Git 友好、可共享且非用户专属的数据快照必须放入 `data/daily_data/`。
新增日志必须放入 `logs/`。
新增外部参考必须放入 `references/`。
新增临时文件必须放入 `temp/`。
任何规则变更必须先修改本文件，再同步调整相关入口文件和说明文档。
