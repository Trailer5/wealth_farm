# 问题路由模块

## 系统模块与目录

本文覆盖系统模块 O2（见 `docs/long_term/系统模块总图.md`），位于编排层（6 层）。

1. `拥有`：`src/research_routing/`（`models.py` 配方与路由结构、`recipes.py` 配方定义、`router.py` 路由器、`executor.py` 配方执行器）。
2. `拥有`：`src/tests/research_routing/`。
3. `有限覆盖`：`src/research_orchestration/routing_adapters.py`（用规划器解析标的、用能力注册表判断 profile 专项缺口、用用户空间核对持仓和读取组合、调用基础流水线和事件名称发现）和 `cli.py` 的 `route`、`run-recipe`、`user-context`、`record-holding` 子命令。
4. `依赖`：`src/research_contracts/`（研究请求与研究产物）、`src/research_ledger/`（用户观点入账、有效动作汇总）。

`research_routing` 不引用 `research_orchestration`；编排模块作为装配根，把适配器注入路由器和执行器，避免同层循环。

## 职责

1. 按“研究对象 × 意图 × 个人化程度”把结构化研究请求匹配到研究配方。
2. 输出每个步骤的当前状态（可执行、部分、规划）、按“必须包含”元素计算的覆盖与正式缺口（缺失系统模块与路线图阶段）、需要用户确认的最少问题，以及“必须避免”的检查项。
3. 执行配方中当前可执行的步骤，不可执行的部分只返回缺口。

自然语言理解由 Agent 完成；本模块不做意图分类。

## 不负责

1. 补齐缺口能力：缺口按路线图阶段建设。
2. Agent 探索与最终报告：仍由单标的主线完成，执行器只完成到基础研究包和 handoff。
3. 调用 smoke 或未接入正式入口的服务（如市场状态计算、回测引擎、质量—估值漏斗）。

## 路由规则

1. 配方按顺序匹配，意图必须与请求完全一致；没有匹配时返回 `unresolved` 和共享对象或意图的配方建议。
2. 标的对象经规划器解析（本地没有时自动补登同代码身份）；未解析或歧义时返回 `unresolved_subject`，`subjects[].issues` 区分有多个候选（`asset_identity_ambiguous`）、没有这个代码（`asset_identity_not_found`）和身份来源远程失败（`asset_identity_lookup_failed`），不猜测。身份已知但缺执行前提（如 `benchmark_unavailable`）时视为已解析，由执行阶段报告阻断。
3. 解析出 profile 后，能力注册表为该 profile 显式声明不支持的决策轨道（`unsupported_lanes`）把对应步骤降为规划，补齐阶段为 7。阶段 7 切片六之后没有 profile 声明不支持的轨道（场外基金时点与仓位已可用）。
4. 必需的用户上下文缺失时返回 `needs_user_context`。持仓以用户空间的记录为准：生产路由注入只读持仓探测，标的配方要求持有该标的，组合配方要求至少一笔持仓；未注入探测时（问题层验收重放）只看请求是否带用户。投资任务、约束、投资偏好与激进含义、原买入理由分别以 `mandate:`、`constraints:`、`preference:`、`thesis:` 开头的 `personal_refs` 表示已提供。生产路由还核对 `preference:` 引用：必须是该用户已记录的偏好版本；“激进含义”还要求该版本带着确认的含义，否则仍是 `needs_user_context`。
5. 只在请求带用户时纳入个人步骤（如组合影响）。检验观点且缺时间窗口时，在用户问题里先问时间窗口，不阻断其余可执行部分。
6. 元素覆盖：所有产出步骤可执行为可执行，全部规划为规划，其余为部分；非可执行元素形成缺口，带系统模块与阶段。
7. 检验观点的配方必须包含反方证据步骤，否则配方定义直接报错。

## 执行规则

1. 路由为 `unresolved`、`unresolved_subject` 或 `needs_user_context` 时不执行任何步骤，不产生副作用。
2. 标的配方：规划 ready 后，请求带 `user_id` 时先保存该用户对该标的的决策简报（评价为准备买入、复核为持仓复核、理解为无决策轨道；用户未给期限时写入默认期限假设，组合角色等缺项保持缺失），再用规划出的任务和简报运行基础流水线，返回 workflow run、handoff、决策简报、报告路径和 Agent 下一步；规划未就绪、用户不存在、基础研究阻断或基础执行校验失败时返回 blocked 步骤并附原因；周期资源公司需要商品权重，提示改用 `run-single`。
3. 观点检验：请求必须带时间窗口（`horizon`），否则只要求补充、不执行其他步骤；用户观点以用户来源、个人可见入账，同一请求重复执行返回同一条目。`view_test` 配方随后生成宏观档案（市场观点生成市场档案）作为 `leading_indicators`，并计算同类历史分布作为 `base_rate`；可证伪改写由 Agent 用 `record-view --supersedes-entry-id` 入账。
4. 市场简报：生成市场档案和宏观档案并入账，计算估值、股债利差和 60 日趋势的同类历史分布；某个档案取数失败时该步骤为 blocked，其余步骤照常执行。
5. 组合读取：请求带用户时，路由中未降为规划的持仓读取步骤（市场简报的组合叠加、观点检验的组合影响、组合改造的组合估值）读取持仓与最近一次组合估值；没有持仓时返回缺口。情景到组合暴露的映射仍由 Agent 完成。
6. 计划（`plan_schedule`）：先汇总该用户自己的有效动作和方向性观点的检查点（客观条目与开发样例不属于任何计划），再生成计划预览（`plan_object`）、复盘节点（`review_nodes`）和同源 HTML（`html_timeline`）；缺偏好时为缺口，偏好与风险约束冲突时为 `needs_input`，取数失败时为 `blocked`。不入账。
7. 行业现状：把 `subject_refs[0]` 对应到申万行业（`resolved_id` 为 `sector:sw:<代码>` 或按名称匹配），生成行业档案并入账；对应不上时 `needs_input`。
8. 发现：提供事件名称发现输入时只运行事件名称发现；否则按 `resolved_id`（`sector:sw:`、`index:`、`market:cn_a`、`symbols:`）或申万行业名称确定范围，运行多策略漏斗（`subject_refs[0].text` 作为范围名）并对前 5 名生成基础包；范围对应不上时 `needs_input`。输出只带前 10 个候选，全量用 `discover --run-id`。
9. 行业观点与推荐：用户观点入账（主体为 `subject_refs[0].text`，补写 `resolved_id` 重跑不重复入账），`resolved_id` 可写多个申万代码；每个行业生成档案和可结算观点模板（行业指数相对沪深300），再在行业并集上运行发现漏斗。组合适配不自动执行，由 Agent 把选定的候选传给 `adjustment-proposal --candidate`。
10. 组合配方：`portfolio_review` 运行组合诊断；`portfolio_rebalance` 依次运行偏好确认、诊断和调整方案（配置、迁移、调整前后情景），偏好的权益区间与风险约束冲突时只给风险预算，其余步骤为 `needs_input` 并列出两个选项；`decision_review` 运行决策复盘与偏好校准。`run-recipe --cash <元>` 把用户说的未投资现金传给这些步骤。
11. 策略（`strategy_evaluation`，阶段 9 切片九）：见下文“策略配方”。
12. 其余配方只返回路由缺口。

## 策略配方

代码：`src/research_routing/executor.py`（`_strategy`、`StrategyRunnerProtocol`）、`src/research_orchestration/strategy_recipe.py`（`StrategyRecipeRunner`，把档案、完整验证与前向跟踪服务接到执行器）。

### 设计说明

1. **对象**：`subject_refs` 的 `resolved_id` 或 `text` 按策略 id 或完整登记名匹配。路由不解析策略（策略不是主数据身份），执行时才匹配；对不上时返回 `needs_input`，带模板列表、`not_expressible` 和登记命令，不按说法猜测规则。没有对象时同样 `needs_input`。
2. **步骤**：每个策略依次输出 `strategy_spec`（档案、状态、策略族尝试数）、`selection_samples`、`backtest_validation`、`regime_analysis`、`attempt_discount`、`forward_tracking`。后四步来自一次 `strategy-evaluate`（每次运行重新验证并新增验证记录，生命周期门槛读最新一条）；取数或信号实现缺失时这些步骤均为缺口并写原因。
3. **样本适用性**：只有选股策略需要历史指数成分，它们的 `selection_samples` 为缺口（时点股票池已含退市股与按公告日的年报，行业范围仍有幸存者偏差）；其余策略写“不适用”。路由的元素覆盖是配方级静态判断，`samples` 仍显示为部分，以执行步骤为准。
4. **分状态摘要**：只列可读状态的结论；策略仓位几乎由某维度决定时（`exposure_driven`，如均线择时对趋势维度）该维度不写入摘要，并注明原因；末尾写截止日所处的状态。
5. **前向**：处于“前向跟踪”或“启用”时运行 `strategy-track`（同一交易日不重复记录），摘要写跟踪起始日、已结算信号数与当前仓位；否则为缺口，门槛满足时给出迁移命令。执行器不自动迁移状态：迁移需要写理由并入账，由 Agent 按指引执行并在回答里说明。
6. **验收**：子代理以新对话在数据库副本上复核“ETF 双动量趋势轮动好不好”与“沪深300 跌破 200 日线清仓、站上再买回好不好”，都只靠指引完成作答；复核提出的摩擦与修复记录在 `docs/当前阶段-策略档案与生命周期.md` 切片九。

## 入口

- `container.router.route(request)`；`python -m src.research_orchestration.cli route --request-json <path>`。
- `container.recipe_executor.run(request, cash=...)`；`python -m src.research_orchestration.cli run-recipe --request-json <path> [--cash <元>] [--discovery-input-json <path>]`。
- `python -m src.research_orchestration.cli vision-acceptance`：重放 `vision_q_v1` 并输出能力覆盖矩阵（`acceptance.py`，规则见 `docs/modules/治理/代表性研究验收模块.md`）。
- `python -m src.research_orchestration.cli user-context [--user-id ID]`：查看用户、持仓（含代码、名称、类型）、最近组合估值、偏好、投资任务与约束快照；`record-holding` 记录用户明确提供的持仓（`--symbol` 本地没有时自动从名录补登）。
- 组合入口：`record-preference`、`portfolio-diagnose`、`allocation-proposal`、`adjustment-proposal`、`portfolio-plan`（含计划 HTML）、`record-trade`、`decision-review`，口径见 `docs/modules/4-个人数据/组合与风险管理模块.md`。
- `python -m src.research_orchestration.cli routine --user-id ID [--as-of-date] [--no-remote] [--skip-archives]`：手动例行命令（`RoutineService`，见下文“手动例行命令”）。
- 各命令的字段、示例和输出读法在 `<命令> --help`（长文本在 `src/research_orchestration/cli_help.py`）；Agent 指引只写流程，见 `.agent/docs/develop/development_rule.md`“Agent 指引”。

## 手动例行命令

路线图把定时运行放在阶段 11；在此之前用一个手动命令完成例行维护，给真实使用期积累前向判断。

### 设计说明

1. 顺序：结算到期检查点（`LedgerSettlementService.settle_due`，对所有用户的到期条目生效）→ 策略前向跟踪（阶段 9 切片八起，对所有“前向跟踪”“启用”的策略运行 `strategy-track`）→ 刷新市场与宏观档案并入账（同内容幂等）→ 检查该用户所有在截止日有效的论点 → 决策复盘摘要（不做偏好校准、不写报告）取到期的计划复盘节点。结算先于跟踪与复盘，前向记录和复盘才看得到新结果。
2. 失败隔离：每一步单独捕获异常，写进 `gaps`，其余步骤照常运行；远程来源失败不阻断论点检查和复盘节点。
3. 输出 `next_actions`：策略已满足启用门槛 → `strategy-archive --transition enabled`；论点偏离或失效 → `exit-plan`；有到期复盘节点 → `decision-review`；只有新结算时也提示 `decision-review`。不自动运行这些后续命令，由 Agent 与用户决定。
4. 不刷新行业档案（一、二级首次运行可能超过 10 分钟），也不自动重跑组合诊断；需要时按 `next_actions` 或用户问题单独运行。
5. 不建定时任务（阶段 11 评估）。

## 测试

`src/tests/research_routing/` 覆盖十个代表性请求的配方与状态、缺口必带模块与阶段、“激进”含义确认、个人步骤、未匹配建议、标的歧义、场外基金时点与仓位可用、持仓未记录时要求用户上下文、观点缺时间窗口时提问、无反方步骤的观点检验配方被拒绝，以及配方元素与长期愿景“必须包含/必须避免”逐字一致、步骤状态与系统模块总图一致；执行器测试覆盖标的配方与直接入口一致、决策简报保存并绑定到基础运行、阻断语义、基础执行校验错误转为阻断、复核持仓意图、观点入账幂等与用户隔离、观点检验生成宏观档案与同类历史、缺少时间窗口、阻断路由无副作用、计划汇总、发现输入和持仓读取，以及计划汇总只含用户自己的条目、组合配方传递现金、偏好与风险约束冲突时只提问、缺基线偏好时先问基线和现金。
