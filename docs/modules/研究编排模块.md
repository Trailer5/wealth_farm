# 研究编排模块

## 职责

`src/research_orchestration/` 把确定性的第一阶段基础收集固化为一次调用：

1. 从代码、资产类型/市场提示和标准化决策目标规划唯一身份、profile 与基础任务。
2. 按 `profile_id` 自动选择正式执行服务。
3. 执行数据、质量、指标、图表、比较、策略和证据阶段。
4. 阻塞时在报告装配前停止。
5. 装配结构化基础研究包并执行程序化复查。
6. 渲染不包含内部版本、ID、枚举和 digest 的基础 Markdown。
7. 通过报告发布服务写入 `report/`。
8. 按 profile、基础问题和决策轨道查询自动化能力、Agent 查询能力、用户上下文与不支持项。
9. 将 complete/partial 基础结果固化为 workflow run 与 handoff；blocked 只保留阻塞状态。
10. 把开放问题和预期证据绑定为显式查询计划，并通过项目公共 service 执行、分类和记账。
11. 从已闭环探索证据装配“考虑、观察、回避、持仓复核或证据不足”之一的结构化适配结论。
12. 在适配结论之后装配带可观察条件、有效窗口、下一可交易时间和跨周期冲突的结构化时点计划。
13. 在用户约束完备后连接 mandate、组合估值、风险输入与时点计划，装配可追溯的结构化仓位区间和分批金额。
14. 将基础包、ready 探索会话和三个决策结果装配为十章节最终决策报告，经结构与 Markdown 双重复查后发布。
15. 将已发布报告的监测计划适配为待确认规则、人工复查或 unsupported 条件，仅在用户确认后注册本地提醒并回写 workflow 状态。
16. 以冻结的新对话场景重跑公共规划，并把实际基础执行、handoff、探索、决策和发布对象适配为可程序化断言的验收观察记录。

基础包完成后，Agent通过 `PersistentResearchExplorationService` 从 `BaselineResearchHandoff` 进入 `ResearchExplorationSession`。问题、假设、查询计划、查询结果、轮次、发现、反证和用户交互形成用户隔离的追加式账本；程序化门禁通过后才能进入最终报告。

## Agent 边界

Agent 不选择 execution service，不手工串联基础阶段，不直接调用 repository 或 Provider，也不拼报告路径。Agent读取基础包后负责按问题价值创建查询计划、多轮探索、解释证据、推演情景、寻找反方，并显式标注 suitability/timing dimension、profile 输入类型、条件状态、周期和有效期；仓位轨道还必须取得用户确认的 mandate、组合约束快照、价格和风险输入。确定性装配器只检查和投影这些输入，不替 Agent 创造论文、预测底部或固定仓位比例。

## 公共入口

- `ResearchExecutionDispatcher`：profile 自动分发。
- `ResearchRequestPlanner`：解析唯一身份、读取 profile assignment 并把用户决策目标映射为可执行基础任务。
- `ResearchCapabilityRegistry`：查询 profile × question × decision lane 的最小能力声明。
- `ResearchOrchestrationPipeline`：执行、装配、复查、渲染和发布。
- `ResearchWorkflowCoordinator`：保存 workflow run，并从 complete/partial 基础结果生成可恢复 handoff。
- `BaselineResearchHandoff`：分离事实章节、partial gaps、blocking gaps、capability gaps 与候选探索方向，并冻结基础 Markdown 及已发布图表 bundle 的摘要 manifest。
- `ResearchReportReviewer`：身份、截止日、三情景、失效条件、事实证据和用户字段泄漏检查。
- `ResearchReportRenderer`：用户 Markdown 白名单渲染。
- `ReportArtifactService`：报告与图表资产发布。
- `DiscoveryOrchestrationPipeline`：推进一个有界指标准备批次，并在准备完成后自动运行发现漏斗。
- `EventNameDiscoveryOrchestrationPipeline`：准备名称候选的事件窗口反应、运行经济无关门禁，并为候选创建探索会话。
- `ResearchExplorationService`：记录多轮问题、假设、查询、发现、用户交互和最终报告准入状态。
- `PersistentResearchExplorationService`：从 handoff 启动、按用户恢复、追加变更并将会话关联回 workflow run。
- `ResearchExplorationQueryService`：校验问题与能力，通过显式公共路由执行 `ResearchQueryPlan`，分类结果并原子更新探索问题和账本。
- `ResearchQueryPlan`、`ResearchQueryResult`：绑定问题、预期证据、公共能力、截止日、结果、证据引用和缺口。
- `SuitabilityAssessmentService`：按 profile policy 从探索轮次装配主论文、收益来源、定价预期、下行、替代方案、机会成本和最强反方，不计算统一分数。
- `SuitabilityAssessment`、`SuitabilityClaimBlock`：输出适配行动、定性置信边界，以及每项结论的证据、限制、时间尺度和截止日。
- `EntryPlanService`：在适配结论之后按 timing policy 装配 act/stage/wait/not_applicable/insufficient 之一，拒绝未入账、错周期、错 profile 和不可观察条件。
- `EntryPlan`、`EntryConditionBlock`：分别保存状态、进入/等待/分批/回避/催化/失效/执行条件、有效窗口、下一可交易时间和跨周期冲突，不含仓位或订单。
- `PositionPlanService`：加载用户所属 mandate、组合估值和约束快照，调用正式预算与组合约束计算器，装配 available/user_context_required/unsupported 之一。
- `PositionPlan`、`PositionCalculationInput`：保存当前权重、目标权重与金额区间、风险预算、压力损失、全部约束上限、绑定约束及与 EntryPlan 条件关联的分批金额，不含订单。
- `FinalDecisionReportAssemblyService`、`FinalDecisionResearchReport`：验证基础 handoff、探索会话、用户简报及适配/时点/仓位身份链，把三轨道、三情景、反方、未知、证据元数据和监测建议冻结为内容寻址对象。
- `FinalDecisionReportRenderer`、`FinalDecisionReportReviewer`：按十章节白名单渲染用户 Markdown，并在结构与正文两阶段检查证据、截止日、用户边界、仓位输入、静态图路径和内部字段泄漏。
- `FinalDecisionReportService`：只在基础包 digest 与 handoff 一致、复用图表/同源数据/metadata digest 与 handoff manifest 一致、图表 metadata 绑定同一标的/截止日且两阶段 reviewer 通过后，通过受限发布方法写入带隐私安全运行指纹的 `*-完整决策报告-YYYY-MM-DD-*.md`；通用 Markdown 发布方法拒绝该文件角色。
- `MonitoringPlan`：保存最终报告发布时的机器观察建议、人工复查条件与复查日期；作为不可变报告快照不保存实际规则引用。
- `FinalDecisionPublicationAttestation`：最终报告发布后持久化用户、workflow、探索/简报/基础 handoff、规范化监测计划、标的、截止日、文件路径和 Markdown digest，供监测入口重新验证。
- `MonitoringHandoffService`、`MonitoringHandoff`：只消费通过上述发布证明复核的报告，把条件显式适配为价格、事件、日期或组合权重候选；准备阶段不创建规则，用户确认后才通过 `AlertService` 内部监测注册口落库，并将状态、规则引用和失败 gap 保存到 workflow run。
- `NewConversationAcceptanceRunner`：通过同一 `ResearchRequestPlanner` 重放 `slice12_v1` 场景，并从公共输出计算身份链、支持/反证轮次、失败语义、正式仓位和最终发布观察；不查询内部 SQLite，不生成 Agent 叙事。
- `ResearchFinding`、`HypothesisStatusEvent`：记录证据等级、截止日、决策轨道、假设影响、证伪条件和不可覆盖的状态历史。
- `create_default_container()`：统一装配SQLite、Provider、五类execution service、能力注册表、workflow coordinator、持久化探索、公共查询路由、适配/时点/仓位装配、组合风险、报告复查发布、本地提醒、监测交接和 `new_conversation_acceptance` 服务。
- `python -m src.research_orchestration.cli plan-single`：从代码或 asset ID 生成结构化身份、profile 和基础任务草稿；歧义时返回候选。
- `python -m src.research_orchestration.cli run-single`：可直接运行并发布单标的基础研究包。
- `python -m src.research_orchestration.cli run-event-name-discovery --input-json <path>`：运行一份带事件、关系证据和反应数据的事件名称发现请求。

## 当前边界

1. 核心流水线通过依赖注入使用已有普通公司、金融机构、周期资源、交易所基金和场外基金五类 execution service。
2. 默认生产容器使用共享SQLite数据库和现有Provider；测试可注入fake容器。
3. Discovery 每次只推进一个有界 batch，远程压力和重试仍由持久化 job 控制；Agent 不参与逐成员循环。
4. 用户报告正文不展示内部审计字段；审计信息保留在结构化对象和图表 metadata。
5. 事件名称发现的外部重大事件首版由人工确认；编排器不把模型生成的事件重要性当成事实。
6. `run-single` 可用显式 `--symbol` 和 `--asset-type open_fund` 从基金公开目录按代码建立类型隔离身份；可选 `--name` 仅用于校验目录名称，同代码股票、交易所基金和场外基金不得合并。
7. 场外基金基础研究包已消费执行结果中的正式净值、风险指标、状态、规模和配置记录；理解型任务不再渲染伪情景或未知反方。
8. 标准执行生成的图表会随 Markdown 发布到 `report/assets/`，正文使用稳定相对路径引用 PNG，同目录保留 SVG、同源数据和 metadata。
9. 场外基金 bundle 中最新可用的官方产品与定期报告快照会渲染为独立事实章节，展示经理、费率、基准、A/C 类规模、配置、持仓和份额变化；部分解析或失败会成为显式非阻塞缺口。
10. 场外基金 benchmark phase 使用官方基准定义计算复合相对表现；成功时输出累计跟踪差值、年化跟踪误差等派生事实，定义不完整、组件来源不可用或覆盖不足时输出对应非阻塞缺口且不降低主流程完成状态。
11. 场外基金执行以完整净值生成标准区间事实，以研究期限窗口生成风险和图表；报告新增“标准区间表现”和“份额、规模与集中度”，累计收益图在基准可用时自动叠加复合基准。
12. 场外基金报告发布前执行必需事实矩阵和结构化复查：核心净值/收益/风险缺失时阻断，官方披露或图表不完整时显式降级；官方事实、派生口径、截止日和每张静态图引用均须通过复查。
13. 场外基金净值远程失败、业务无记录和未分类链路错误使用不同缺口代码；真实主 smoke 也以不同退出状态区分远程来源、业务数据和代码回归。
14. `plan-single` 在代码唯一时使用持久化 profile assignment 或资产类型默认 profile；同代码跨股票、ETF、场外基金歧义时返回候选，不按代码外形猜测。
15. 用户购买目标与基础 question 分离：场外基金当前始终规划为 `understanding`，但决策目标保留给后续探索。
16. 当前规划器只生成任务草稿，尚未自动运行基础流水线；基础流水线完成后会自动保存 `ResearchWorkflowRun`，complete/partial 生成 `BaselineResearchHandoff`，blocked 不生成 handoff 或探索会话。
17. 能力注册表声明“系统可做什么”，实际 handoff 声明“本次取得什么”；注册表不能覆盖本次执行缺口，单次成功也不能扩张注册表中的不支持项。
18. workflow run 和 handoff 持久化在 `research_workflow_runs` 与 `baseline_research_handoffs`；探索快照和追加式账本持久化在 research_state 所属表，并由 workflow run 保存唯一 session 关联。探索开始后同一 workflow run 的基础结果不可覆盖。
19. `mark_ready` 要求至少一轮结构化探索、无开放 blocking 问题、请求决策轨道有发现、适配轨道完成替代方案、主论文有证伪条件、冲突关闭且最强反方已评估。
20. `container.queries` 已显式路由数据访问、官方文档证据、基准、事件、同行、用户研究状态和组合快照；外部官方网页只登记 Agent 已复核的来源，不提供通用爬虫。
21. 查询必须绑定开放问题、声明能力、预期证据和完成条件。success、partial、业务无数据、远程失败、用户上下文不足、不支持和执行失败分开记账；查询不会自动回答问题，Agent 解释证据并记录结构化轮次后再显式关闭。
22. 当前不会从 handoff 缺口静默生成和执行固定查询清单；Agent 仍按决策影响、不确定性和成本选择下一查询。
23. `container.suitability.assemble(...)` 只承认探索轮次 `evidence_refs` 中已入账证据；事实/推断还必须声明限制、时间尺度、profile 输入类型和适配维度。跨轨道论文、假设或未知发现不能支持 consider。
24. 普通公司、金融机构、周期资源、ETF 和场外基金使用独立 profile policy。consider 还要求替代方案与机会成本指向同一可比暴露；缺失决策简报、核心反方或核心证据时返回 insufficient。
25. `SuitabilityAssessment` 不含时点和仓位；三轨道仍由独立对象承接，只有 `FinalDecisionReportAssemblyService` 在最终报告层做并列投影，不合并为总分。
26. `container.entry.assemble(...)` 只消费 timing track 中显式分类且已入账的事实/推断。每项条件必须带可观察键、周期、有效起止、证据和限制；策略 pass/fail 不直接映射为 act。
27. act/stage 要求执行周期的状态、进入、等待、回避、催化、失效、交易日历和执行约束完整。所有条件有效窗口必须有交集，下一可交易候选必须落在交集内并与 profile/执行周期一致。
28. 短期与长期状态分别保存在 condition block；发现冲突但未记录冲突时为 insufficient，已确认冲突时为 wait，不求平均分。场外基金当前缺少正式 timing execution，保持 insufficient。
29. `EntryPlan` 不包含目标价、底部预测、目标仓位、分批金额或自动订单；分批规则只描述条件顺序，金额由仓位计划决定。
30. `container.position.assemble(...)` 以 `ResearchDecisionBrief`、`SuitabilityAssessment`、`EntryPlan`、`PositionCalculationInput` 以及用户所属 `InvestmentMandate`、组合估值和 `PortfolioConstraintSnapshot` 为输入。用户、标的、workflow、周期、截止日、币种或引用不一致时拒绝装配。
31. available 目标上限必须是风险预算、压力损失、单标的集中度、正相关、流动性、现金底线和计划资金上限的最小值。区间内持仓为 maintain，超限持仓为 reduce；未持有和已持有使用不同动作语义。
32. EntryPlan 为 stage 时，分批比例必须由约束快照确认并与活动分批条件逐项关联；wait/insufficient 不生成执行分批。结果是规划边界而非订单，不做取整、杠杆、做空或均值—方差优化。
33. 普通公司、金融机构、周期资源和 ETF 支持仓位装配；场外基金个性化执行仓位当前显式 unsupported。缺少 mandate、组合、价格、风险或用户约束时为 user_context_required，不给固定比例。
34. `container.final_decision.assemble_and_publish(...)` 要求 ready 探索、已发布基础包和三个结构化决策结果。官方证据显示链接、发布日期和可选页码；派生证据显示方法与限制；所有正文引用必须由 `FinalEvidenceCitation` 覆盖。
35. 最终文件名固定使用 `*-完整决策报告-YYYY-MM-DD-<运行指纹>.md` 角色；运行指纹防止同标的同日跨用户覆盖，不展示原始用户或 workflow ID。不得把 `*-基础研究包-*` 改名充当最终报告。图表只引用 `report/assets/` 下已经发布且 metadata 匹配的相对静态路径，不复制内部 metadata 到正文。
36. `MonitoringPlan` 由时点失效条件和主论文证伪条件装配，发布时只允许 user_confirmation_required/unsupported，且 `alert_rule_refs` 必须为空。
37. `container.monitoring.prepare(...)` 只接受已发布且 reviewer 通过的最终报告；只有显式 `MonitoringRuleBinding` 与受支持观察键匹配时才生成价格、事件或组合权重候选，报告复查日期单独生成日期候选。人工条件和未适配条件不会丢失。
38. `container.monitoring.confirm_and_activate(...)` 要求用户选择具体候选，先持久化 activation_pending，再创建本地规则。研究规则只有在 workflow 与 handoff 同时保存对应授权后才参与评估；分步持久化中断时规则保持惰性，重试会恢复引用。规则和触发 alert 携带 workflow、最终报告、监测计划、原条件及证据引用；注册失败形成可重试 gap，不修改已发布报告结论。
39. `container.new_conversation_acceptance` 只接受各阶段公开对象和显式记录的用户问题，不把构造的通过状态当作真实研究。正常决策场景要求至少一轮支持证据和一轮反证，身份歧义在 task 前停止，基础 blocked 不得产生 handoff，远程失败与业务无数据保持不同 outcome。
