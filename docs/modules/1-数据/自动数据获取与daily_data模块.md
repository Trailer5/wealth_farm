# 自动数据获取与 daily_data 模块

## 模块职责

自动数据获取与 `daily_data` 模块负责把“哪些标的需要持续关注”和“哪些容易消失的公开信息需要持续积累”连接起来，并通过可审阅、可重放、可质量拦截的自动任务保存共享事实。

本模块的核心职责按优先级排列：

1. 维护自动跟踪标的集合。集合必须覆盖所有用户的 active 自选、所有用户的非零持仓、公共自选和人工固定标的。
2. 围绕自动跟踪标的持续收集新闻、公告、基金披露、研报元数据、监管信息和来源健康记录。
3. 保存信息与标的之间的关系、关系类型、证据、置信度和确认状态。
4. 使用 JSONL、JSON 和必要的稳定表格文本，把增量事实发布到独立 `daily_data` 仓库。
5. 为统一数据访问、Web 信息流、事件抽取、提醒和 AI 研究提供可追溯输入。

`daily_data` 是共享事实快照和自动任务产物，不是用户数据库，也不是“凡是能抓的数据都每天抓一次”的缓存仓库。

## 当前主要矛盾

项目当前的主要矛盾不是缺少日线。股票和 ETF 日线已经可以通过统一数据访问层在用户研究时按需获取，并通过多 Provider fallback 写入 SQLite。

真正缺少的是：

1. 自动任务不知道所有用户和公共列表正在关注哪些标的。
2. 通用新闻 Provider 尚未建立，易消失的信息没有持续积累。
3. 通用文本与标的之间的直接、间接和主题关系尚不能可靠判断。
4. 公告、研报和监管信息虽然已有部分 Provider，但尚未进入统一增量 JSONL 发布链路。
5. 质量、去重、修订和人工确认边界尚未覆盖信息型数据。

因此，自动化建设顺序必须先解决跟踪集合、信息模型、来源和关联，再启用定时任务。不得因为日线 writer 已经存在就把日线更新误当成 daily_data 的核心目标。

## 不负责的内容

本模块不负责：

1. 保存 `user_id`、关注理由、标签、持仓数量、报告、提醒处理状态或 AI 会话。
2. 实现外部 Provider。外部访问由数据获取底层接口模块负责。
3. 决定文本中的实体对应哪个主数据对象。身份、别名和主体关系由主数据模块负责。
4. 独立完成信息与标的的语义关联。候选关联和事件抽取由事件与知识抽取模块负责。
5. 替代统一数据访问层。上层不得直接依赖 daily_data 文件路径。
6. 把所有日线、分钟线或实时行情作为默认定时任务。
7. 在准入条件未满足时自动提交和推送结果。

## 自动跟踪标的集合

### 输入来源

自动跟踪集合必须合并：

1. 所有用户空间中的 active 自选项。
2. 所有用户空间中的非零持仓。
3. 项目级公共自选列表。
4. 人工固定标的。

同一 `asset_id` 只保留一项，但应记录不含用户身份的来源类型，例如 `user_watchlist`、`holding`、`public_list` 和 `pinned`。

### 共享投影

共享投影只能包含：

1. 稳定 `asset_id`。
2. 标准代码、名称、资产类型、市场和交易所。
3. 跟踪来源类型。
4. 是否启用。
5. 首次加入和最近同步时间。

共享投影不得包含：

1. `user_id`。
2. 自选列表名称。
3. 关注理由和标签。
4. 持仓数量、成本和币种。
5. 用户报告、提醒和任务状态。

所有用户自选和持仓当前位于本地 SQLite。GitHub-hosted runner 无法直接读取用户电脑上的数据库。因此必须先实现运行在本地应用或可访问用户数据库环境中的“跟踪集合同步器”，再把去除用户信息后的集合物化到 `daily_data`。

在跟踪集合同步器完成前，现有 `tracked_assets.json` 只是日线 runner 原型配置，不是完整的自动跟踪集合。

## 每日信息对象

### 优先收集内容

1. 通用公司、基金和市场新闻。
2. 交易所和 CNINFO 公告。
3. 基金公司和基金披露。
4. 证监会、交易所等监管公开信息。
5. 研报元数据。
6. 来源健康、抓取游标和失败摘要。

### 暂不作为每日核心任务

1. 股票和 ETF 日线：默认按需获取到 SQLite；只有明确的共享历史发布任务才写入 daily_data。
2. 分钟线和实时行情：不适合 Git 日常增量。
3. PDF、图片和大体量正文：保存元数据、URL、哈希和提取摘要，二进制文件放在其他存储或 artifact。
4. 全市场无差别抓取：初期只围绕自动跟踪集合。

## 统一信息与关联模型

信息记录至少需要：

1. 稳定 `record_id`。
2. `information_type`，例如 `news`、`disclosure`、`research_report`、`regulatory`。
3. 标题、摘要、来源 URL、来源名称、发布时间和抓取时间。
4. 来源记录 ID、内容哈希、schema version、revision 和 operation。
5. `related_assets`。

每个关联至少需要：

1. `asset_id`。
2. `relation_type`，例如 `direct_symbol`、`issuer`、`manager`、`holding`、`underlying`、`industry`、`theme`。
3. `confidence`。
4. `method`，例如 `provider_scope`、`exact_symbol`、`alias_rule`、`entity_rule`、`ai_classifier`、`human_confirmed`。
5. 支持该关系的标题片段、命中代码、别名或其他证据。
6. `review_status`，例如 `confirmed`、`candidate`、`rejected`。

按证券代码调用的官方公告和研报接口可以产生高置信度直接关联。通用监管页面、市场新闻和主题新闻不得因为出现模糊简称就直接归入标的目录。

## 目录与文本格式

标的专属信息使用：

```text
data/daily_data/
  assets/
    <market>/
      <exchange>/
        <symbol>/
          asset.json
          news/<year>/<month>.jsonl
          disclosures/<year>/<month>.jsonl
          research_reports/<year>/<month>.jsonl
          regulatory/<year>/<month>.jsonl
```

共享候选和状态使用：

```text
data/daily_data/
  shared/
    market_news/
    regulatory/
    data_source_health/
    unresolved_relations/
  manifests/
    tracked_universe.json
    source_cursors.json
  schemas/
```

JSONL 记录必须使用稳定字段顺序和 UTF-8。修订使用相同 `record_id`、递增 revision 和 `upsert`/`delete` operation。相同信息涉及多个标的时可以复制到多个标的目录，但必须保留相同 `record_id` 和完整关系集合，由统一访问层去重。

## 模块关联与责任边界

### 用户空间与研究状态

保存所有用户自选、持仓和关注状态，提供跨用户只读聚合接口。它们不写 daily_data。

### 主数据与标的身份

把用户代码、公司、基金、发行人、管理人、指数、行业、主题和来源别名映射为稳定身份，为信息关联提供候选和证据。

### 数据获取底层接口

负责调用公告、基金披露、研报、监管和未来新闻 Provider，返回标准化候选信息。它不决定最终关联，也不写 daily_data。

### 事件与知识抽取

负责把候选信息关联到一个或多个标的，生成关系证据和结构化事件。确定性规则优先；AI 只处理模糊候选。

### 数据质量与可观测性

负责检查必需字段、稳定 ID、重复、时间、来源、关联证据、revision 和发布状态。失败项不得进入自动提交。

### 自动数据获取与 daily_data

负责编排跟踪集合、增量游标、抓取、关联、质量门禁、JSONL writer 和发布。它不重复实现上述模块的业务判断。

### 统一数据访问

向 Web、报告、提醒和 AI 返回合并后的信息流，处理 daily_data 与 SQLite 去重、新鲜度和按需补取。

### Web UI

展示自动跟踪状态、信息流、来源和关联证据，并提供候选关系确认、拒绝和重新绑定入口。

## 正确的自动流程

1. 从所有用户自选、非零持仓、公共列表和 pinned 配置生成跟踪集合候选。
2. 通过主数据服务解析并去重为稳定 `asset_id`。
3. 把不含用户信息的跟踪集合投影同步到自动任务可访问的位置。
4. 按来源游标为每个标的获取新增候选信息。
5. 标准化记录并生成稳定 `record_id`。
6. 使用 Provider 查询范围、代码、别名、主体和主题规则生成标的关系候选。
7. 高置信度关系直接确认；模糊关系进入 AI 或人工确认。
8. 运行信息型质量检查、去重和 revision 规则。
9. 写入 JSONL、manifest、游标和质量摘要。
10. 只有整批任务通过发布门禁后才提交 daily_data。
11. 统一数据访问层读取新 commit 并向 Web、提醒和 AI 提供信息。

## 定时任务准入条件

同时满足以下条件后才能重新启用 schedule：

1. 跟踪集合可以稳定读取所有用户 active 自选、非零持仓、公共列表和 pinned 标的。
2. 共享投影不包含用户归属信息。
3. 至少一个信息型 Provider 通过真实增量验证。
4. 信息 schema、稳定 ID、去重、revision 和游标规则完成。
5. 直接和模糊关联边界完成，并有人工复查入口。
6. 信息型质量门禁和失败隔离完成。
7. 手动任务连续验证成功且不会提交错误或空结果。

在这些条件满足前，GitHub Actions 只允许 `workflow_dispatch`，不得配置 schedule。

## 当前能力与缺口

当前已经存在可复用的日线 CSV writer、质量门禁 runner、tracked assets 原型和手动工作流。这些代码保留为按需共享日线工具，但不代表 daily_data 核心自动化已经完成。

当前已有官方公告、基金披露、证监会公开信息和个股研报元数据 Provider，也有公告标题事件规则和 PDF 处理能力。

当前缺口是：

1. 跨用户和公共列表的自动跟踪集合聚合与同步。
2. 通用新闻 Provider。
3. 信息统一 schema 和 JSONL reader/writer。
4. 通用信息与标的关联模型。
5. 新闻实体、别名、发行人、底层和主题关联。
6. 模糊关系 AI/人工确认。
7. 信息型质量门禁、来源游标和增量发布。
8. Web 信息流和关系复查入口。

本模块当前暂停，不设独立短期开发计划。现有手动工具保留；世界状态的定期刷新在 `docs/long_term/发展路线图.md` 阶段 5 评估，新闻与信息增量在阶段 10、长期自动运行在阶段 11 评估，均需用户确认后启用。
