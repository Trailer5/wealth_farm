# 用户空间与研究状态模块

## 有效上下文设计说明（2026-11-18）

`UserSpaceContextReader` 优先读取数量持仓，没有数量时使用截止日期前最新 HoldingWeights；返回 holdings_basis、原始比例快照及名称/代码。未知 quantity 保持 null，现金/类别桶及 proxy 不伪装成实际持仓。has_positions 读取同一视图，避免比例已登记仍被问是否持有。数量与比例不自动混算；数量持仓没有完整历史，输出明确其为当前快照。

user-context 的 as_of_date 限定可见偏好和比例快照；execution_context 单列当时可知的有效计划编号、修订、约束、确认来源及未决事项，当前/未来日期只使用现在已知信息。计划例外不回写通用偏好，不从文字约束推算数值风控。历史计划按 UTC 日末信息截止查询，不声称完整历史数量持仓重建。

节点可附 rule_refs（rule_id/content_hash），计划可附 rule_exclusions（编号到不适用理由）。P1 只保存引用，不依赖研究产物层；原研究读取、覆盖检查与失效保护在编排层。源规则变化阻塞关联节点直接完成/执行，不删除历史、不猜测语义或授权交易。

## 系统模块与目录

本文覆盖系统模块 P1（见 `docs/long_term/系统模块总图.md`），包含两个代码模块：

1. `src/user_space/`：用户空间模型、当前用户上下文、用户偏好和数据归属辅助逻辑。
2. `src/research_state/`：自选、持仓、分析报告、决策简报、探索快照和追加式账本 repository。

对应测试位于 `src/tests/user_space/` 和 `src/tests/research_state/`。偏好、决策历史与行为记录规划在 `docs/long_term/发展路线图.md` 阶段 8 扩展。

## 一、用户空间与数据归属

### 职责

让多个用户分别维护自己的自选、关注理由、持仓、偏好、报告、提醒和研究任务上下文。

本部分解决的是数据归属和正常使用时的记录区分，不是用户之间的安全隔离。当前目标是避免不同用户的数据互相混淆，而不是防止用户主动查看其他用户的数据。

### 不负责的内容

当前阶段不负责：

1. 防止用户主动窥探其他用户的数据。
2. 严格身份认证和授权。
3. 行级安全、租户级数据库隔离和每用户独立数据库。
4. 加密隔离、密钥管理和合规审计。
5. 面向不可信用户的多租户安全。

Web UI 后续可以使用简单登录、会话或用户选择器识别当前用户空间，但这些机制不构成安全边界。项目不得把当前能力描述为隐私保护或安全多租户。

只有用户明确提出新的安全目标，或项目进入专门的安全 milestone 后，才重新设计认证、授权、审计和租户隔离。

### 目录与脚本范围

#### 拥有

1. `src/user_space/`：用户空间模型、当前用户上下文、用户偏好和数据归属辅助逻辑。
2. `src/tests/user_space/unit_tests/`：用户空间选择、默认用户、数据归属和查询过滤测试。
3. `src/tests/user_space/smoke_tests/`：多用户正常使用流程验证。

#### 依赖

1. `src/data_store/`：保存用户、用户偏好和带用户归属的业务记录。
2. 存储与统一访问模块：在访问自选、持仓、报告和任务时传递当前 `user_id`。
3. Web UI：提供当前用户空间选择或简单身份识别。
4. AI harness：为报告、会话和分析任务附加当前用户归属。

#### 有限覆盖

1. 自选、持仓、组合、报告、提醒和 AI 任务模块中的 `user_id` 字段与查询条件。
2. `data/database/` 中按用户归属的数据表。

### 数据归属规则

共享行情、财务、公告、新闻和主数据不需要因用户不同而重复保存。

自动数据任务可以读取所有用户空间中的 active 自选和非零持仓，用于计算“需要持续跟踪哪些标的”。该读取必须经过明确的聚合服务，只输出去重后的 `asset_id` 和不含用户身份的来源类型。

以下数据必须包含 `user_id` 或等价用户空间字段：

1. 自选和关注理由。
2. 持仓、交易记录和组合配置。
3. 用户偏好和界面设置。
4. 用户保存的报告和分析结论。
5. 提醒规则和提醒处理状态。
6. AI 会话、分析任务和用户确认状态。
7. 单标的用户决策简报和缺失上下文状态。

查询这些数据时必须使用当前用户空间作为普通业务过滤条件。该过滤用于正确展示数据，不视为防攻击授权检查。

跨用户自动跟踪聚合是普通用户查询规则的唯一明确例外。聚合结果不得返回 `user_id`、关注理由、标签、持仓数量、成本、报告或其他用户状态。

### 初期实现原则

1. 系统提供一个默认用户空间，单用户使用时不增加额外交互。
2. 多用户使用时，可以通过简单用户选择、登录名或会话字段确定当前 `user_id`。
3. 多个用户可以共用同一个 SQLite 数据库。
4. 按用户归属的表优先增加 `user_id` 字段和必要组合索引，不拆分独立数据库。
5. 不引入角色、权限矩阵、资源 ACL 或复杂身份供应商。
6. 共享数据和按用户归属的数据必须在 schema 与模块文档中明确区分。

### 安全升级点

当前实现应保留以下最小升级点：

1. `users` 使用稳定、不可因显示名变化而改变的内部 `user_id`。
2. 按用户归属的记录使用 `user_id` 外键或等价稳定引用，并建立正常查询需要的组合索引。
3. Web UI、AI harness 和研究任务通过统一 `UserContext` 或等价上下文传递当前用户，不在各模块自行解析用户名。
4. 用户归属数据通过明确的 service 或 repository 读写，不让 UI 直接拼接用户过滤 SQL。
5. 用户及用户归属记录保留 `created_at`、`updated_at` 等基础时间字段，便于未来迁移和审计扩展。

这些升级点只保证未来可以接入认证和授权，不代表当前已经实现安全隔离。

当前不得为了未来可能性预建密码、token、角色、权限、ACL、行级安全、租户密钥或每用户独立数据库。未来如需安全能力，应把身份提供方映射到现有稳定 `user_id`，并在统一服务边界增加授权检查。

### 输入与输出

输入包括当前用户标识、用户偏好和各业务模块提交的用户归属数据。

输出包括当前用户上下文、按用户过滤的业务记录和用户偏好。

### 当前能力与缺口

当前已建立 `src/user_space/`、`users` schema、默认用户、稳定 `user_id` 和 `UserContext`。自选、持仓、分析报告、决策简报、提醒和 AI 任务已经按 `user_id` 归属，Web 可以切换当前用户空间。

当前缺口是用户偏好和面向自动跟踪的跨用户去身份聚合接口。该聚合接口完成前，云端 daily_data 任务不能声称覆盖所有用户关注标的。

## 二、研究状态持久化

### 职责

保存用户在研究过程中产生的长期状态，让研究流程不依赖对话记忆或临时文件。

当前重点保存：

1. 自选列表和关注理由。
2. 当前持仓数量、成本和备注。
3. 用户保存的分析报告和结论。
4. 单标的用户决策简报、决策轨道和缺失上下文。
5. 与 workflow run 和 handoff 关联的探索快照及追加式账本。

### 不负责的内容

当前版本不负责：

1. 券商级交易流水、成交回报和税费核算。
2. 复杂组合优化和收益归因（属于组合与计划能力，见 `docs/long_term/发展路线图.md` 阶段 8）。
3. 新闻、公告和研报原始数据存储。
4. 策略运行和回测。
5. Web UI。
6. 安全多租户、角色和权限。

### 目录与脚本范围

#### 拥有

1. `src/research_state/`：自选、持仓、分析报告、决策简报、探索快照和追加式账本 repository。
2. `src/tests/research_state/unit_tests/`：状态读写、用户归属和查询测试。
3. `src/tests/research_state/smoke_tests/`：后续手动研究闭环验证。

#### 依赖

1. `src/user_space/`：提供稳定 `user_id` 和默认用户上下文。
2. `src/master_data/`：所有自选、持仓和报告通过 `asset_id` 引用标的。
3. `src/data_store/`：共享 SQLite 数据库文件。
4. 存储与统一访问模块：为研究提供行情和其他分析输入。
5. 自动数据获取模块：只读聚合 active 自选和非零持仓，生成去用户化跟踪候选。

#### 有限覆盖

1. 用户空间部分中的默认用户和 `UserContext`。
2. 后续报告证据引用协议。

### 数据边界

共享行情、财务、公告和主数据不得复制到用户研究状态表中。

自选、持仓、分析报告、决策简报和探索会话必须包含 `user_id`。查询必须按当前用户空间过滤，避免正常使用时混淆，但当前不把该过滤作为安全授权机制。

本部分必须提供自动跟踪候选的聚合边界。该边界扫描所有用户的 active 自选和非零持仓，输出 `asset_id` 及来源类型，不输出用户身份、关注理由、标签、数量、成本或备注。

分析报告可以保存 Markdown 正文和少量 JSON 元数据。当前不为报告设计复杂富文本格式。

### 初期对象

1. `watchlists`：用户的自选列表。
2. `watchlist_items`：列表中的 `asset_id`、关注理由、标签和状态。
3. `holding_positions`：用户当前持仓数量、平均成本、币种、备注和用户所述的首次买入日（`first_bought_on`，可空；旧库在初始化时补列）。只有当前快照，没有逐笔交易，因此行为偏差提示无法从历史识别“亏损后加仓”。
4. `analysis_reports`：用户保存的标题、摘要、Markdown 正文、状态和标的关联。
5. `research_decision_briefs`：用户对单一标的的意图、是否/时点/仓位轨道、持仓状态、期限、组合角色、mandate/约束快照引用和缺失上下文。
6. `research_exploration_sessions`：当前探索快照、workflow run、handoff、决策简报和用户归属。
7. `research_exploration_ledger_entries`：问题、查询计划与结果、轮次、发现、假设变化和 ready 状态的不可更新追加记录。

### 输入与输出

输入包括 `UserContext`、`asset_id`、自选信息、持仓信息、分析报告内容、`ResearchDecisionBrief` 所需决策上下文和结构化探索变更。

输出包括按用户过滤的自选、当前持仓、报告、决策简报、探索快照、追加式账本及缺失用户上下文，以及供自动跟踪模块使用的去用户化标的候选集合。

### 当前能力与缺口

当前已建立 `src/research_state/`、默认自选、多个自选列表、当前持仓增删改查、Markdown 分析报告、决策简报和探索状态持久化。决策简报按 `user_id + asset_id` 更新；探索状态按用户与 workflow run 唯一关联，快照保存问题的查询历史、最近结果和查询缺口，账本通过数据库门禁保留完整计划与结果。

黄金 ETF `518880` 已跑通真实数据访问、质量门禁、自选、持仓、报告保存和重启读取。

当前缺口是跨用户自动跟踪候选聚合、公共自选边界、交易流水、持仓历史和最终报告证据。问题到公共项目能力的查询执行记录已由研究编排服务写入探索账本；workflow run 由研究编排模块拥有，本部分只保存探索侧稳定关联。InvestmentMandate 与组合约束快照由组合模块统一拥有，本部分只保存稳定引用，不复制数值风险约束。

## 三、执行计划注册与全局日历

### 职责与公共入口

P1 保存用户的执行承诺、稳定编号、不可变修订和逐次处理记录，支撑 P3 巡检；不取代 R5 判断账本或 R6 组合计划。拥有 `src/user_space/plan_schedule.py`、`src/user_space/plan_registry.py` 及 `src/tests/user_space/unit_tests/test_plan_registry.py`；公共编排位于 `src/research_orchestration/execution_plans.py`，生产容器的 `execution_plans` 服务负责用户有效性与归属检查。没有新增模块层或依赖偏离。

Agent 使用 `plan-register`、`plan-show`、`calendar`、`task-resolve`、`plan-review`。结构化字段、完整示例和结果读法由对应 `--help`、方法文档字符串及输出提供；工作流见 `.agent/docs/research/playbooks/execution_plans.md`。当前开发切片为 `docs/当前阶段-计划注册与执行日历.md`。

### 持久化

- `execution_plans`：用户、稳定 plan_id、用户范围内唯一 registration_key。
- `execution_plan_revisions`：只追加完整快照与实际 recorded_at。包括目标、来源、状态、节点、修订理由；不改已有研究 Plan 契约。
- `execution_task_records`：逐次处理记录，含节点、周期实例、采用的计划修订、原截止时间、结果、证据、下一检查时刻及成交/用户确认引用。

本地数据库仍为 `data/database/wealth_farm.sqlite3`，表由所属 repository 幂等初始化。写入以 `BEGIN IMMEDIATE` 串行化，计划修订使用 expected_revision 乐观并发检查；同一登记键与相同快照无操作，同一处理 request_id 仅允许相同内容重试。没有删除历史的公共接口。用户过滤是数据归属，不是安全授权。

### 设计说明

1. **日历是查询视图，不是第二份事实。** 从有效计划节点按需展开，查询不写入实例、不联网、不修改状态。原研究证据通过 source_refs 连接报告、辩论、观点、动作、可观测量；引用不会自动校验正文或最新有效性，处理任务时 Agent 必须核实。
2. **身份与变更。** plan_id 不随快照变化；节点 task_id 在计划内唯一。完整修订替换后续日历安排，删除节点的定义仍可从旧修订回看。已有处理记录的节点不可原地改条件，使用新 task_id 表示新承诺，避免旧的完成状态误用于新条件。暂停和关闭同样是带理由的修订。
3. **时间。** 日期在任务 IANA 时区内覆盖全天；带偏移时刻为精确时间，输入偏移必须匹配指定时区。窗口起点决定可处理时刻、deadline 决定逾期。周期用当地自然日、保持当地钟点，每次有稳定 occurrence；必须有结束日，最多 10001 次，不静默截断。重复规则不含统一窗口 deadline。Windows 显式依赖 tzdata。遇到夏令时不存在/歧义的周期时刻拒绝展开，应改登记明确节点。
4. **不确定事件。** 不解析自然语言触发器，也不预测披露时间。日期未知时登记下一检查节点；财务数据以实际披露可得时间为准。自然日不是交易日历，不伪装成交易日/连续收盘规则引擎。Agent 核实规则后记录结论。
5. **处理状态。** completed 仅完成观察/研究；action 只有 executed 且附真实成交或明确用户确认引用才能记执行，系统不接经纪商。not_triggered/cancelled 关闭本次实例；证据不足用 blocked，等待条件/确认用 deferred/awaiting_confirmation，均须指定未来 next_check。延期保留原期限，重查时可再次逾期；周期实例各自关闭。
6. **依赖。** 首版仅支持计划内非周期前置节点，拒绝不存在和循环依赖；只有 completed/executed 解除，未触发、取消或跨计划引用不能自动授权行动。跨计划现金、仓位与风险冲突由 Agent 使用最新组合入口核查，不自动交易。
7. **历史。** 所有记录时间是实际 UTC 登记时间，不允许回填。calendar 的 at/through 决定日程窗口，默认使用当前已知计划；历史研究必须同时传 known_at 排除后来修订与处理，且不得晚于当前时刻。按时完成指按时登记完成，不推断真实成交日。撤销/修订不能改变历史记录。
8. **复盘。** handling_counts 按每个实例最后结果计数，deferrals/blocked_checks 按处理次数计，late_closures 按原期限统计逾期关闭实例；保留每次理由供反省，不以完成率推出盈亏、择时贡献或预测命中率。后者仍由原账本结算。

### 能力边界与局限

已接入手动 `routine` 的独立 calendar 步骤；其他步骤失败不会阻断日历，反之亦然。单独 calendar 可完全离线运行。原有组合 review_nodes、辩论 signposts 和仓位复评仍由原流程管理，未登记的旧节点不自动进入新日历，避免将历史建议当成已确认承诺；新计划须按工作流显式登记，并以同一研究引用关联。首版不提供自动抽取、发布时原子注册、后台定时、通知、UI、条件表达式求值、收益归因或自动写持仓。

### 2026-11-18 复核补充

- 计划可选 constraints 与 uncertainties，逐项随日历返回，避免独立执行节点时漏掉全权益、现金、仓位上限和尚待确认的例外。它们是原计划文字，不是自动约束引擎，展示不等于确认或自动判定。
- 迁移节点可选 source_excerpt，用原文措辞对照 source_refs；后续变更与其他节点字段一样受不可变历史约束。不得靠摘录存在就声称所有衍生说明完全等义，仍需人工核对逻辑、单位和覆盖范围。
- 有界周期在登记时完整校验；夏令时不存在/歧义时刻应在登记前拒绝，而非数月后毒化全局日历。历史节点展开失败单独进入 gaps，其他节点继续返回；缺口透传到 plan-review 和 routine 顶层。
- 持续观察可用一个不设经济到期的节点，每次检查后 deferred 并给 next_check；这样不擅自添加周期终止日。一次检查完成不等于整条投资规则失效。固定节点到期不会自动删除未完成事项。
- 迁移必须区分行政检查日、实际公告/披露日和交易触发日。中旬可用行政窗口，未知上市日与交易日计数不能猜测；多季条件不得被单季或累计值替代。一个买入批次只登记一次，多个替代触发器不得变成多个额度。
