# 模块文档索引

## 职责

`docs/modules/` 记录每个模块的职责、边界、能力、输入、输出、依赖、处理目录和脚本范围。模块文档只记录模块本身的长期事项，不记录短期开发计划、开发步骤和进度 tracking。

短期开发计划、当前阶段说明、跨模块协调事项和开发 checklist 必须放在 `docs/` 根目录下的临时开发文档中。

每份模块文档必须尽量包含：

1. 模块职责。
2. 模块不负责的内容。
3. 处理的目录、脚本和测试范围。
4. 输入、输出和依赖模块。
5. 当前已有能力和缺口。
6. 当前存在开发计划时，记录对应的 `docs/` 根目录文档。

## 模块目录划分规范

每个模块的核心代码应尽量放在自己的 `src/<module>/` 主目录下。

模块目录划分必须保留弹性。共享基础设施可以拥有独立目录，例如 `src/data_store/`、`src/document_processing/`、未来可能出现的 `src/common/` 或跨模块运行框架。共享基础设施不应为了形式统一被强行塞进某个业务模块。

模块文档必须说明相关目录和脚本的关系：

1. `拥有`：该目录或脚本属于本模块主职责，新增同类能力应优先放入这里。
2. `依赖`：该目录或脚本由其他模块或共享基础设施负责，本模块只调用它。
3. `有限覆盖`：该目录或脚本本身不属于本模块，但其中某一段链路会影响本模块能力。

目录、文档和脚本命名必须尽量自解释。项目维护者和 Agent 在没有历史上下文时，应能通过路径和模块文档判断用途、归属和边界。

推荐目录结构：

1. 模块源码：`src/<module>/`。
2. 单元测试：`src/tests/<module>/unit_tests/`。
3. smoke 测试：`src/tests/<module>/smoke_tests/`。
4. 模块文档：`docs/modules/<层目录>/<模块名>.md`，层目录见下文“目录结构”。
5. 短期开发计划：`docs/短期开发计划-<模块名>.md` 或 `docs/当前阶段-<模块名>.md`。

跨模块测试入口使用 `src/tests/run_all_unit_tests.py`。`src/unit_tests/` 和 `src/smoke_tests/` 不得重新建立。

## 文档粒度

1. 一个系统模块默认对应一份模块文档，系统模块见 `docs/long_term/系统模块总图.md`。
2. 一个系统模块包含多个代码模块时，在同一份文档内分节描述；只有各代码模块内容都足够充分且相对独立时，才拆成多份文档。
3. 参考手册（如因子手册）可以独立成文，与所属模块文档放在同一目录。
4. 不建立没有代码归属、只复述长期需求的综述型文档；这类内容属于 `docs/long_term/`。
5. 模块文档不复制长期愿景中的研究纪律、时间尺度定义和路线图中的能力需求，只引用。
