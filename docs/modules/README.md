# 模块文档索引

## 职责

`docs/modules/` 记录每个模块的职责、边界、能力、输入、输出、依赖、处理目录和脚本范围。模块文档只记录模块本身的长期事项，不记录短期开发计划、开发步骤和进度 tracking。

短期开发计划、当前阶段说明、跨模块协调事项和开发 checklist 必须放在 `docs/` 根目录下的临时开发文档中。

每份模块文档必须尽量包含：

1. 模块职责。
2. 模块不负责的内容。
3. 处理的目录、脚本和测试范围。
4. 输入、输出和依赖模块。
5. 当前已有能力和缺口。
6. 当前存在开发计划时，记录对应的 `docs/` 根目录文档。

## 模块目录划分规范

每个模块的核心代码应尽量放在自己的 `src/<module>/` 主目录下。

模块目录划分必须保留弹性。共享基础设施可以拥有独立目录，例如 `src/data_store/`、`src/document_processing/`、未来可能出现的 `src/common/` 或跨模块运行框架。共享基础设施不应为了形式统一被强行塞进某个业务模块。

模块文档必须说明相关目录和脚本的关系：

1. `拥有`：该目录或脚本属于本模块主职责，新增同类能力应优先放入这里。
2. `依赖`：该目录或脚本由其他模块或共享基础设施负责，本模块只调用它。
3. `有限覆盖`：该目录或脚本本身不属于本模块，但其中某一段链路会影响本模块能力。

目录、文档和脚本命名必须尽量自解释。项目维护者和 Agent 在没有历史上下文时，应能通过路径和模块文档判断用途、归属和边界。

推荐目录结构：

1. 模块源码：`src/<module>/`。
2. 单元测试：`src/tests/<module>/unit_tests/`。
3. smoke 测试：`src/tests/<module>/smoke_tests/`。
4. 模块文档：`docs/modules/<模块名>.md`。
5. 短期开发计划：`docs/短期开发计划-<模块名>.md` 或 `docs/当前阶段-<模块名>.md`。

跨模块测试入口使用 `src/tests/run_all_unit_tests.py`。`src/unit_tests/` 和 `src/smoke_tests/` 不得重新建立。

## 基于长期路线图的模块开发顺序

长期路线图已经确定先补齐核心基础模块，再推进分析、产品和 AI harness。模块开发顺序如下：

1. 文档治理和目录对齐：确认 `docs/`、`docs/modules/`、`docs/long_term/`、`data/database/`、`data/daily_data` 和 `temp/` 的职责。
2. 主数据与标的身份模块：统一股票、基金、指数、公司、行业和外部数据源代码映射。
3. 数据获取基础层：稳定 `src/data_src/` provider、真实验证、温和访问、接口状态记录和不稳定接口隔离。
4. 统一数据访问与持久化模块：统一 `daily_data`、SQLite 和远程补取入口，建立数据需求与新鲜度策略。
5. 数据质量与可观测性模块：结构化记录任务状态、数据源健康、质量检查、失败类型和影响范围。
6. 最小用户空间：建立默认用户、稳定 `user_id` 和普通数据归属查询。
7. 研究状态持久化：沉淀自选、当前持仓和用户分析报告，并提供去用户化自动跟踪候选。
8. 事件与知识抽取模块：建立信息—标的关系后，把公告、新闻、研报、财报和基金披露转成结构化事件。
9. 因子与特征工程模块：统一技术指标、基本面指标、事件因子、风险因子和组合特征。
10. 组合与风险管理模块：覆盖持仓、仓位、收益、回撤、暴露、归因和风险监控。
11. 自动数据获取模块：聚合所有用户和公共关注标的，持续收集新闻、公告、研报和监管增量，准入完成后再启用 GitHub Actions schedule。
12. 提醒与触发器模块：基于价格、公告、财报、策略信号、数据质量和持仓风险生成提醒。
13. Web 服务与用户界面模块：提供数据健康、自选、详情、策略、组合、提醒和报告入口。
14. AI harness 模块：组织用户意图、上下文、工具、模型、证据引用和结果落库。
15. 用户空间与长期运维：补齐备份、迁移和长期运行机制，不把安全多租户作为当前目标。

当前开发计划是 `docs/短期开发计划-daily_data跟踪集合与信息增量.md`。
