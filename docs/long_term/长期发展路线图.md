# Wealth Farm 长期发展路线图

## 定位

Wealth Farm 是个人投研和数据底座项目。长期目标不是只做一个数据抓取脚本集合，而是形成一套可以持续扩展的投研工程系统：

1. Agent 能理解项目规则、调用项目脚本、辅助开发和辅助研究。
2. 数据获取层能稳定访问、校验和沉淀 A 股、基金、披露、财报、研报等公开信息。
3. 自动化任务能在无服务器环境中持续补齐日常数据。
4. 分析模块能围绕技术指标、基本面指标、策略研究和回测持续迭代。
5. 持久化层能保存用户关注、自选、持仓、分析结论、新闻、报表和任务过程。
6. 网络服务和用户界面能承载日常研究交互。
7. AI harness 能在 Web 场景中组织数据、工具、模型调用和分析流程。
8. 用户空间能让多个用户分别维护自选、持仓、偏好、报告和研究上下文。

除上述层级外，主数据与标的身份、数据质量与可观测性、事件与知识抽取、因子与特征工程、组合与风险管理、提醒与触发器应从一开始纳入核心功能规划。这些模块不只是后期增强项，它们会影响数据模型、分析接口、Web UI 和 AI harness 的基础设计。

本路线图记录长期方向和阶段边界。具体短期任务应落在 `docs/` 根目录的短期计划中，模块边界和接口细节应落在 `docs/modules/`。

## 当前基线

当前数据获取底座已经具备较多基础能力。主线已经覆盖 A 股日线和周线、ETF 实时与日线、场内基金多源实时、场外基金净值和申赎状态、A 股三大报表、财务指标、官方披露、PDF 下载和解析、OCR 队列、财报字段抽取等能力。

当前主线不应依赖已记录为停用或不稳定的接口。后续如果需要实时行情、分钟线、行业成分、基金穿透持仓或研报正文，应独立设计 provider、限流、缓存、合法数据来源和验证标准。

`data/daily_data` 已作为独立 Git submodule 存在，负责保存围绕自动跟踪标的持续积累的新闻、公告、研报元数据、监管信息和其他可共享增量事实；`data/database/` 负责本地 SQLite、按用户归属的状态、按需补取的行情和高频关系查询。两者作为统一数据访问层的并列数据源，不要求把 `daily_data` 强制导入 SQLite。

自动跟踪标的必须来自所有用户 active 自选、非零持仓、公共列表和 pinned 标的的去用户化并集。用户状态保留在 SQLite，daily_data 只保存标的身份投影，不保存任何用户信息。

## 长期原则

数据优先。所有分析、AI 交互和用户界面都必须建立在可追溯的数据基础上。数据记录应尽量保留来源、抓取时间、解析版本和质量状态。

统一访问。分析、Web UI、AI harness 和 Agent 研究流程不得各自直接拼接 `daily_data`、SQLite 和远程 provider。它们必须通过统一数据访问层描述数据需求，由访问层完成身份解析、新鲜度检查、按需补取、合并和来源追踪。

模块优先。先把数据获取、数据存储、分析、回测、报告、AI harness 和 Web 服务的边界做清楚，再把它们组合成产品体验。

结构自解释。目录、文档、模块边界和开发计划必须承担项目记忆的作用。新增目录和文档应让用户和 Agent 在缺少历史上下文时也能判断用途、归属和边界。

模块归属保持弹性。业务模块应尽量拥有自己的主目录，但数据存储、文档处理、通用工具和跨模块运行框架等共享基础设施可以独立存在。模块文档必须说明相关目录是模块拥有、模块依赖，还是有限覆盖。

官方披露优先。对基金持仓、财报字段、公告正文等关键事实，长期应优先依赖官方披露和可验证文件，而不是不稳定第三方封装。

温和访问。真实外部数据验证和自动任务必须尊重上游压力，默认使用限流、退避、缓存、增量更新和失败隔离。

主要矛盾优先。自动化必须先回答“跟踪谁、持续收集什么、如何判断相关、如何确认质量”，再决定调度频率。不得把已经写好的某类 writer 反过来当作自动化目标。

研究可复现。分析结论不能只保存最终文字，还要保存输入数据范围、策略版本、参数、运行时间和关键中间结果。

Agent 分工清晰。`.agent` 主要服务 IDE 内开发和研究执行引导；AI harness 主要服务 Web 用户界面中的数据流、工具流和模型交互。

用户归属保持轻量。自选、持仓、偏好、报告、任务记录和 AI 上下文必须预留用户维度，用于正常使用时区分记录。当前用户空间不是安全边界，不为防止用户主动窥探而增加复杂鉴权、行级安全或租户隔离。

## 核心补充模块

以下模块应作为核心功能的一部分纳入早期规划。它们可以分阶段实现，但数据模型和接口边界需要尽早预留。

### 主数据与标的身份模块

主数据模块负责统一股票、ETF、LOF、场外基金、指数、公司、基金公司、行业、交易所代码和外部数据源代码之间的映射。它是行情、财报、公告、基金披露、研报、持仓和分析结果能够正确关联的前提。

早期应先解决证券代码、市场、名称、简称、上市状态、基金类型、产品类型和数据源代码映射。后续再扩展公司主体、管理人、行业分类、指数成分、基金经理和同一主体的跨市场关系。

### 数据质量与可观测性模块

数据质量与可观测性模块负责回答“数据是否可信、任务是否正常、失败发生在哪里”。它应覆盖数据源健康、任务运行状态、质量检查、缺失范围、异常值、解析失败和自动化任务结果。

这个模块与 `logs/` 有密切关系，但不等同于普通日志模块。`logs/` 适合保存运行过程中的详细文本、错误堆栈、调试信息和审计日志；数据质量与可观测性模块应把可查询、可聚合、可展示的事实落入数据库，例如任务开始和结束时间、数据源状态、检查项结果、失败类型、影响范围和恢复状态。

值得长期沉淀的不是所有日志文本，而是日志背后的结构化状态。Web UI、GitHub Actions 摘要、Agent 研究流程和 AI harness 都应优先读取这些结构化状态，再按需跳转到详细日志。

### 事件与知识抽取模块

事件与知识抽取模块先负责判断公告、新闻、研报、财报和基金披露与哪些标的相关，再把重要事实转成结构化事件。它应服务标的详情、提醒触发、策略研究、AI 分析和历史报告。

早期可优先覆盖按代码查询的官方公告直接关联，再覆盖业绩预告、业绩快报、分红、回购、减持、增持、重大合同、诉讼仲裁、监管处罚、基金经理变更、基金规模异动和申赎状态变化。每个信息关系和事件都应保存来源、原文位置、抽取时间、规则或模型版本、置信度和人工确认状态。

### 因子与特征工程模块

因子与特征工程模块位于原始数据和策略之间，负责把行情、财务、基金、事件和组合数据转成可复用特征。技术指标、基本面指标、事件因子、风险因子和组合特征都应尽量通过统一接口提供。

这个模块的价值是减少策略重复计算，并让回测、报告和 AI 分析使用同一套特征定义。每个因子应记录输入数据范围、计算版本、参数、适用资产类型和缺失处理方式。

### 组合与风险管理模块

组合与风险管理模块负责从单标的研究推进到组合视角。它应覆盖持仓、仓位、成本、收益、回撤、波动、相关性、集中度、行业暴露、风格暴露、基准偏离和收益归因。

早期可以先支持用户持仓快照、简单组合收益、行业集中度、单标的贡献和回撤监控。后续再扩展风险模型、情景分析、压力测试、组合优化和调仓建议。

### 提醒与触发器模块

提醒与触发器模块负责把系统从被动查询推进到主动监控。它可以基于价格、估值、成交量、回撤、公告事件、财报变化、基金规模、申赎状态、策略信号、数据质量异常和持仓风险触发提醒。

早期提醒不需要复杂消息系统，可以先落库为待处理提醒，并在 Web UI 或报告中展示。后续再扩展到邮件、Webhook、桌面通知或其他渠道。

## 分层路线

### 1. Agent 协作层

开发阶段的 Agent 入口已经由 `.agent/AGENT_README.md`、`.agent/SKILL.md` 和 `.agent/docs/` 承担。长期需要继续补足两类引导。

第一类是开发引导，包括目录职责、模块边界、测试要求、真实数据验证规则、计划维护规则和跨模块协作规则。这部分要保持简短、稳定、可执行，不把临时想法写成长期规则。

第二类是研究分析引导。用户未来应能要求 Agent 直接使用本项目脚本和流程完成分析工作，例如更新数据、读取自选池、运行指标分析、执行回测、生成报告草稿、沉淀研究结论。为此需要建立研究任务规范、脚本调用手册、输出报告模板、数据质量检查步骤和失败处理规则。

长期目标是让 Agent 在 IDE 中既能开发项目，也能按项目约定执行研究流程，但 `.agent` 不直接替代 Web harness。

### 2. 数据获取基础层

数据获取是所有上层能力的基础。长期应把现有 provider 继续整理成稳定的数据源边界。

核心工作包括：

1. 为每个 provider 维护能力矩阵、输入输出、频率限制、失败模式和替代来源。
2. 为 `DataFetchService` 明确主线任务，例如证券基础信息、日线行情、基金净值、财报、公告、研报元数据和文档解析。
3. 建立数据质量校验，包括非空校验、日期连续性、复权字段一致性、财务字段单位、公告文件类型、PDF 文件头和解析成功率。
4. 建立数据源健康状态，把成功、失败、空结果、上游异常、解析异常和限流异常分开记录。
5. 把高压力、不稳定或探索性接口保持在实验边界，不纳入默认任务链。

这一层的验收标准不是“接口被调用过”，而是“可重复获得非空真实数据，并能记录来源、状态和失败原因”。

### 3. 自动数据获取层

自动数据获取由自动跟踪集合、数据获取 Provider、信息关联、数据质量、daily_data writer 和发布工作流共同组成。GitHub Actions 只是最后的执行环境，不是模块目标本身。

第一步是确定自动跟踪集合。系统必须聚合所有用户 active 自选、所有用户非零持仓、公共自选和 pinned 标的，按 `asset_id` 去重，再生成不含用户信息的共享投影。云端任务无法直接读取本地 SQLite，因此必须有明确的本地同步、self-hosted runner 或受控 API 链路。

第二步是持续积累容易消失或持续新增的信息。优先级为通用新闻、官方公告、基金披露、监管信息、研报元数据和来源健康。股票和 ETF 日线已经可以在研究时按需获取到 SQLite，不作为默认每日任务；已有 CSV writer 只承担明确的共享历史发布。

第三步是建立信息与标的的关系。按代码查询产生高置信度直接关系；名称、发行人、管理人、指数、底层、行业和主题关系必须保存证据、方法、置信度和确认状态。模糊信息先进入候选区，不得直接进入标的信息流或触发提醒。

第四步才是发布。JSONL 用于新闻、公告、研报元数据、监管信息、关系和来源观察；JSON 用于跟踪集合、游标、schema 和质量摘要；CSV 仅用于明确需要共享的稳定表格快照。自动任务必须有稳定 ID、增量游标、去重、revision、质量门禁和失败隔离。

在跟踪集合、至少一个信息型 Provider、关系判断、质量门禁和手动连续验证完成前，GitHub Actions 只允许手动触发，不得启用 schedule。

### 4. 核心分析模块

核心分析模块是项目最需要长期持续迭代的部分。它应建立在数据底座稳定之后，分成技术分析、指标分析、研究策略、回测评估和报告生成几个方向。

技术分析应先覆盖基础指标和组合信号，例如均线、趋势、动量、波动率、成交量、回撤、相对强弱和形态类指标。指标实现需要有统一输入输出和测试样本，避免每个策略重复处理行情数据。

基本面和指标分析应围绕财报字段、估值、成长、盈利质量、现金流、负债、基金规模、基金持仓披露、行业和公告事件逐步展开。早期可以先做可解释的指标集合，不急于引入复杂模型。

研究策略应把“选股/选基假设”表达成可运行对象，保存筛选条件、数据窗口、参数、版本和输出集合。策略不是一次性脚本，而是可反复运行、比较和修订的研究资产。

回测模块应先做清晰可信的低频回测，包括交易日历、调仓周期、手续费、滑点、停牌和数据缺失处理。后续再扩展组合归因、风险指标、基准对比、滚动窗口和参数稳定性分析。

报告生成应服务研究闭环。每次分析应能输出结构化结果、图表数据、自然语言摘要和可持久化的 report 记录。

### 5. 数据持久化层

持久化层同时包含统一数据访问边界。一次请求必须先由主数据模块解析 `asset_id`，再检查 `daily_data` 和 SQLite 的覆盖范围、新鲜度和质量；数据不足时才调用数据获取模块补取。新鲜度必须按新闻、日线、净值、财报、公告等数据类型分别定义。

持久化层需要从“保存原始数据”扩展到“保存研究状态”。长期应至少覆盖以下对象：

1. 用户自选、关注池、观察理由和关注状态。
2. 用户持仓、交易记录、成本、仓位和组合快照。
3. 历史分析结论、报告、策略运行结果和回测结果。
4. 关键新闻、公告、研报元数据、财报字段和事件标签。
5. AI 分析任务、输入上下文、工具调用记录、模型输出和人工确认状态。
6. 数据源健康、数据版本、解析版本和任务运行日志索引。

SQLite 是本地工作数据库，负责按用户归属的状态、主数据解析状态、主动补取数据和高频关系查询。`daily_data` 可以直接读取，导入 SQLite 只是可选物化或缓存优化。

这一层应尽早确定 schema 版本和迁移策略。未确立正式生产 milestone 前，可以直接修正不合理设计；一旦报告、持仓和用户数据开始长期使用，就必须引入迁移和兼容约束。

### 6. 网络服务与用户界面

当关注点从模块开发转向日常研究时，Web UI 应成为主要交互界面。它不需要一开始复杂，但要围绕研究工作流设计，而不是只展示数据库表。

早期界面应优先支持：

1. 数据健康总览，展示最近更新时间、失败数据源和缺失范围。
2. 自选和持仓管理，支持关注理由、标签、分组和状态。
3. 标的详情页，整合行情、财务、公告、基金信息、研报元数据和历史分析。
4. 策略和指标运行入口，支持选择标的池、参数、时间范围和输出报告。
5. 报告列表和报告详情，支持查看历史结论、输入数据和后续跟踪。
6. AI 分析入口，允许用户围绕某个标的、组合或策略发起受控分析任务。

Web 服务应通过项目内部 API 访问数据和分析模块，不应让 UI 直接拼接底层脚本细节。

### 7. AI API 与 harness 工程

AI harness 是 Web 用户界面使用 AI 能力时的工程层。它和 `.agent` 的目标不同：`.agent` 是让 IDE 内 Agent 理解如何开发和执行项目；harness 是让产品内 AI 功能稳定组织数据、工具、模型和结果。

harness 应长期解决以下问题：

1. 用户意图识别，把“分析某个标的”“比较组合”“解释回测”“生成报告”等请求转成任务规格。
2. 上下文装配，从数据库、报告、行情、财务、公告、新闻和用户持仓中抽取必要上下文。
3. 工具编排，按任务调用数据查询、指标计算、策略运行、回测、报告生成和引用检查。
4. 模型交互，管理 prompt、结构化输出、流式响应、重试、成本和错误处理。
5. 结果落库，把 AI 输出和支撑数据、工具调用、模型版本、用户确认状态一起保存。
6. 质量控制，区分事实、推断和建议，保留引用，避免把缺失数据包装成确定结论。

AI 分析可以保持灵活，但输入输出边界必须结构化。每次 AI 分析应至少保存任务规格、用户问题、输入清单、检索到的上下文、工具调用记录、模型请求参数、模型输出、结构化结论、引用对象和人工确认状态。

研究证据与引用不一定在早期独立成一个完整产品模块，但必须作为 AI harness、报告模块和持久化层的共同协议存在。证据单元可以指向数据库记录、数据源状态、公告或 PDF 文档片段、财报字段、事件记录、因子计算结果、回测运行结果或历史报告。AI 输出中的关键结论应尽量引用这些证据单元，而不是只保存一段无法回溯的自然语言。

长期目标是让 AI 成为研究流程的一部分，而不是一个脱离数据底座的聊天窗口。

### 8. 用户空间与数据归属

早期最低要求是让多个用户分别维护自选、持仓、偏好、报告和 AI 任务。持久化层应使用 `user_id` 或等价用户空间字段区分记录。

当前用户空间只解决正常使用时的数据归属和展示，不是安全边界。当前目标不包括防止用户主动查看其他用户的数据，也不要求行级安全、每用户独立数据库、权限矩阵或加密隔离。

用户空间按以下方式推进：

1. 提供单用户默认空间，单用户使用时不增加额外交互。
2. 自选、持仓、偏好、报告、提醒和 AI 任务按 `user_id` 区分。
3. Web UI 可以使用简单用户选择、登录名或会话字段识别当前用户空间。
4. AI harness 使用当前 `user_id` 装配正确的用户上下文，但当前不把它作为防恶意越权机制。
5. 多个用户共用同一个 SQLite 数据库，不为当前目标拆分独立数据库。

当前实现应保留最小安全升级点：稳定内部 `user_id`、统一用户上下文、用户归属数据的 service/repository 边界，以及基础创建和更新时间字段。这些设计允许未来接入认证与授权，但当前不预建密码、角色、ACL、行级安全或独立租户库。

只有用户明确提出新的安全需求或项目进入专门的安全 milestone 后，才重新规划严格认证、授权、审计和租户隔离。

## 阶段推进

### 阶段 0：规划与治理基线

目标是把项目文档、目录、规则和当前状态对齐。完成后，Agent 和用户都能知道长期路线图、短期计划、模块文档分别写在哪里。

主要交付包括长期路线图、短期数据源与数据库计划、`data/database/` 与已有 `data/datebase/` 命名问题处理、`daily_data` 职责说明、README 基础说明和当前模块文档索引。

### 阶段 1：数据底座稳定

目标是把已有数据接口从“可调用”推进到“可验证、可落库、可追踪”。这一阶段应优先修正 schema、数据质量、失败状态和真实验证流程。

主要交付包括 provider 能力矩阵、主数据初版、统一数据请求边界、双数据源职责、数据源健康表、数据质量检查表、真实数据温和验证流程、SQLite schema 维护规则、公告/PDF 解析主线和不稳定接口隔离策略。

### 阶段 2：研究对象与持久化

目标是让项目开始保存研究状态，而不只是保存原始数据。

主要交付包括默认用户、稳定 `user_id`、自选、关注理由、当前持仓和分析报告的初版 schema。策略运行、回测、事件、提醒和 AI 任务在手动基础闭环完成后继续扩展。

### 阶段 3：核心分析 MVP

目标是形成可重复运行的分析闭环：选择标的池，运行指标或策略，生成结果，保存报告，并能后续对比。

主要交付包括技术指标库、基础财务指标、因子与特征工程接口、策略对象、低频回测、组合与风险指标、报告生成和对应单元测试。

### 阶段 4：自动日常数据

目标是在手动研究闭环稳定后，让自动任务围绕所有用户关注和公共关注标的持续积累易失信息。

主要交付包括跨用户跟踪集合、去用户化投影、统一信息与 relation schema、新闻/公告/研报候选、JSONL writer/reader、增量游标、revision、去重、质量摘要、人工复查和发布规则。

阶段 4 已启动，但当前仅完成日线 writer 和 runner 原型。该原型保留为按需共享历史工具；定时任务已暂停，不能将其视为阶段 4 完成。当前应优先建设跟踪集合和信息增量链路。

### 阶段 5：Web 研究界面

目标是把日常研究入口从 IDE 和脚本逐步迁移到 Web UI。

主要交付包括数据健康页、自选/持仓页、标的详情页、策略运行页、报告中心和基础服务 API。

### 阶段 6：AI harness 集成

目标是让 Web UI 中的 AI 分析可以受控调用项目数据和分析工具，并把结果持久化。

主要交付包括任务规格、上下文装配器、工具编排器、模型调用适配、结构化输出、证据引用协议、任务日志和报告落库。

### 阶段 7：用户空间与长期运维

目标是把个人项目中的研究能力整理成可长期运行、可扩展、可迁移的系统。

主要交付包括轻量用户空间、默认用户、稳定 `user_id`、统一用户上下文、按用户归属的数据查询、数据库迁移、备份恢复、数据任务监控、成本监控和正式 milestone 兼容策略。严格安全多租户不属于当前阶段交付。

## 关键未定事项

以下事项会影响后续设计，不能在没有决策时写成事实：

1. 本地用户关注集合以本地同步、self-hosted runner 还是受控 API 投影给云端任务。
2. 通用新闻来源、授权边界、抓取频率、正文保留范围和替代来源。
3. 行业、主题、底层资产等间接关系的自动确认阈值和人工复查标准。
4. `data/datebase/` 是否为拼写错误，是否需要迁移到 `data/database/`。
5. Web 前端技术栈和部署方式。
6. AI harness 使用的模型供应商、调用方式、成本限制和隐私边界。
7. 项目何时进入需要兼容历史 schema 和历史报告的正式 milestone。

## 开发步骤拆解

1. 建立长期文档基线：补齐本路线图、当前阶段计划和模块文档索引。
2. 对齐数据目录：确认 `data/database/`、`data/daily_data` 和临时数据目录的职责。
3. 建立主数据与标的身份模块：统一证券、基金、公司、行业和外部数据源代码映射。
4. 稳定数据获取主线：完善 provider 能力矩阵、质量校验、真实验证和健康状态。
5. 建设统一数据访问：统一身份解析、双数据源查询、新鲜度策略、按需补取和来源追踪。
6. 建设数据质量与可观测性：把任务状态、质量检查和失败影响范围结构化落库。
7. 建设最小用户空间与研究持久化：先实现默认用户、自选、当前持仓和分析报告。
8. 建设核心分析模块：先做可解释指标、因子特征、低频策略、组合风险和可复现回测。
9. 手动研究闭环稳定后建设自动信息增量：先同步所有用户和公共关注标的，再建设新闻/公告/研报关联、质量和发布，最后启用 schedule。
10. 建设 Web 服务和 UI：围绕研究流程提供数据健康、自选、详情、策略、组合、提醒和报告入口。
11. 建设 AI harness：把用户意图、上下文、工具、模型、证据引用和结果落库串成闭环。
12. 推进用户空间和运维：补齐默认用户、用户归属字段、普通查询过滤、备份和迁移。
