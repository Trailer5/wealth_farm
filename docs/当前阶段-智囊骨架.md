# 当前阶段：智囊骨架

状态：completed（2026-10-26）。第五节的设计决策已于 2026-10-25 由用户确认。

本文是 `docs/long_term/发展路线图.md` 阶段 4 的计划。它吸收了已搁置的 `docs/当前阶段-单标的决策闭环与结算.md` 中可结算决策与前向结算的设计，并推广到所有研究对象。

## 一、阶段定位

阶段 4 结束时，任意代表性问题都能进入同一套研究组织：

1. Agent 把用户问题转成结构化的研究请求（对象、意图、个人上下文、深度、截止日、期限）。
2. 代码把请求路由到研究配方，告诉 Agent 哪些步骤可以执行、需要哪些用户信息、哪些部分是正式缺口及其补齐阶段。
3. 可执行的步骤由配方执行器调用现有公共入口完成；单标的研究不再需要 Agent 手工把规划结果交给基础执行。
4. 状态评估、观点、可结算动作和计划使用统一结构，进入只追加的观点账本；价格类判断可以到期前向结算。
5. 十个代表性问题冻结为可重放的验收场景，形成按问题的能力覆盖矩阵。

本阶段只建骨架，不补宏观、市场、行业、组合等数据和分析能力；这些能力缺失时由骨架如实报告缺口。

涉及系统模块：C1、R5、O2、O3、G4（编号见 `docs/long_term/系统模块总图.md`）。

## 四、设计原则

1. **Agent 理解，代码路由**：自然语言到结构化请求由 Agent 完成；代码不做意图分类，只校验请求、路由配方和执行确定性步骤。
2. **缺口是一等输出**：配方中每一步都有状态（可执行、部分、缺口）；缺口带缺失的系统模块和路线图阶段，不用自由发挥补齐。
3. **用户观点是待检验的输入**：用户观点以“用户来源”的观点入账，配方必须包含反方证据步骤，不能把它写成前提。
4. **发布即入账，入账可重建**：账本条目是已发布判断的确定性投影；写入失败可以从发布记录幂等补录，不依赖跨仓库事务。
5. **只追加**：账本条目、结算和复盘发布后不得修改或删除；修订以新条目引用旧条目。
6. **前向结算**：参考价使用发布后第一个可成交价格；历史回放产生的 Agent 判断不入账。
7. **契约最小化**：计划等后续阶段才产出的对象只冻结最小必需字段，后续阶段按 v1 规则直接修正，不增加兼容层。
8. **先守住依赖方向**：分层依赖检查先于新模块落地，新代码不得新增偏离。

## 五、设计决策

以下决策已于 2026-10-25 确认。修改任何一项时，先改本节，再改相关切片和代码。

1. **新模块位置与名称**：`src/research_contracts/`（C1，共享契约）、`src/research_ledger/`（R5，观点账本与结算）、`src/research_routing/`（O2，问题路由与研究配方）。CLI 子命令继续放在 `src.research_orchestration.cli`：新增 `route`、`run-recipe` 和 `settle-ledger`。
2. **共享词汇迁移不保留兼容转发**：遵守“未定版阶段不加兼容层”的规则，一次性更新全部导入。
3. **意图理解由 Agent 完成**：代码不做自然语言意图分类。
4. **默认结算检查点**（自然日，从参考价日期起算）：短期 30；中短期 90、180；中长期 180、365；长期 730、1095。
   - 检查点落在非交易日时，取该日之前最近一个交易日的收盘价；场外基金取该日之前最近的确认净值。
   - 观点自带的到期日晚于最后一个默认检查点时，追加为最后一个检查点。
5. **概率只接受发布前显式填写的区间**，不强制；没有概率的观点只做命中与超额统计。
6. **单标的判断到账本的映射**：
   - 适配 consider、avoid → 相对基准的方向性观点；
   - watch、hold_review、insufficient → 入账但不做方向性判定，只记录期间表现；
   - 时点 act、stage、wait → 可结算动作，触发条件引用原条件的可观察键和有效窗口；
   - 仓位 → 作为对应动作的数量规则引用，不单独结算。
7. **用户观点默认入账**：在观点检验请求中给出的用户观点，以用户来源、个人可见的方式入账，后续可以看到它的结算；用户明确拒绝时不入账。
8. **分层检查测试目录**：`src/tests/architecture/unit_tests/`。
9. **校准摘要延后**：本阶段只做结算和复盘记录；按类型的校准摘要等真实结算样本积累后再建，不在本阶段用 fixture 冒充。

## 六、目标契约

第 1、2 部分是切片三的冻结字段，已于 2026-10-25 由用户复核确认；与原草案的差异在每部分末尾列出。第 3 部分在切片四、五冻结，第 4 部分在切片六、七冻结。

### 1. 研究请求

```text
ResearchRequest
  request_id
  subject_type        # macro | market | sector | asset | strategy | portfolio
  subject_refs        # SubjectRef(text 原文, resolved_id 可空)；sector、asset、strategy 至少一个
  intents             # 有序、非空、不重复：understand | evaluate | discover | test_view | decide | plan | review
  personalization     # none | optional | required；portfolio 必须为 required
  user_id             # personalization=required、有 user_view 或 personal_refs 时必填
  user_view           # 用户观点原文；intents 含 test_view 时必填，否则必须为空
  depth               # quick | standard | deep，默认 standard
  as_of_date
  horizon             # 可空；需要时由配方要求补充
  personal_refs       # mandate、约束快照等已有 ID；personalization=none 时必须为空
```

与草案的差异：

1. `intent` 改为有序的 `intents`。Q3 是“评价 + 决定动作”，Q9 是“检验观点 + 寻找机会”，单一意图表达不了；路由按整组意图匹配配方。
2. 新增约束：portfolio 必须结合用户；sector、asset、strategy 必须有对象引用；`test_view` 必须带用户观点原文。

### 2. 研究产物

```text
StateAssessment     # 对象在截止日的状态
  assessment_id / subject_type / subject_id / as_of_date
  dimensions        # AssessmentDimension(name, value, historical_percentile 0–1 可空, evidence_refs 非空)
  label / confidence(low | medium | high)
  change_signals    # 会改变判断的可观察信号

View                # 可证伪的观点
  view_id / subject_type / subject_id
  origin(system | user) / user_id   # user 来源必须有 user_id；system 来源不得带 user_id
  proposition / horizon / as_of_date / expires_on(晚于 as_of_date)
  claim             # 可空；有 claim 即方向性观点
                    # ViewClaim(metric_key, comparison, threshold)
                    # comparison: outperform | underperform（对照结算规则的基准，threshold 为最低超额，可空）
                    #           | above | below（threshold 必填）
  support_refs / counter_refs / base_rate_ref(可空)
  confidence / probability(可空，ProbabilityInterval: 0 ≤ low < high ≤ 1)
  falsifiers / implications
  settlement_rule   # 方向性观点必填；非方向性观点可选，只记录期间表现

SettlementRule
  method(price_relative | metric_observation) / observed_id
  benchmark_id / alternative_id     # 只用于 price_relative；outperform、underperform 必须有 benchmark_id

SettleableAction    # 可结算动作
  action_id / asset_id / action_type(buy | add | reduce | exit | hold)
  horizon           # 评估期限，决定结算检查点（切片五补充）
  trigger           # ActionTrigger(kind: scheduled | conditional, valid_from, valid_until)
                    #   scheduled：scheduled_on；conditional：observability_key + condition
  quantity_rule     # QuantityRule(kind: position_plan | user_defined | unavailable, reference 或 description)
  invalidation_refs
  settlement_rule   # 必须为 price_relative，且 observed_id 等于 asset_id

Plan                # 本阶段只冻结最小结构，阶段 8 扩展
  plan_id / user_id / as_of_date / version(≥1)
  actions           # 非空；定期节点和条件节点就是动作的 trigger
  targets           # TargetRange(subject_id, metric_key, low < high, window_start < window_end, basis, probability 可空)
  review_nodes      # 非空；ReviewNode(review_on, focus)
```

与草案的差异：

1. `subject` 拆成 `subject_type` 与 `subject_id`；`View` 增加 `as_of_date`，作为期限和结算的起点。
2. 判定结构固定为“指标 + 比较方式 + 阈值”，相对基准统一由结算规则提供，避免判定与结算各写一份基准。
3. 动作类型不含 `wait`：等待某个条件再买，表达为带条件触发的 `buy`；没有可观察条件的等待不构成动作，按非方向性观点入账。
4. 计划直接内嵌动作，不再用节点引用动作 ID；定期与条件节点由动作的触发方式区分。
5. 所有对象序列化时拒绝未知字段；数值用十进制字符串，避免浮点误差。

### 3. 账本与结算

```text
LedgerEntry         # 只追加；entry_id 由 entry_type + artifact_id 确定
  entry_id / entry_type(assessment | view | action | plan)
  scope(objective | personal) / user_id(仅 personal)
  source_ref        # 发布记录（final-report:<report_id>）、配方运行或用户请求
  artifact_id / subject_id / as_of_date / effective_until   # 从产物派生的查询列
  payload / content_digest / supersedes_entry_id / recorded_at

Settlement          # 只追加；settlement_id 由内容确定（不含 computed_at）
  entry_id / checkpoint_date
  status(settled | data_insufficient | not_settleable) / claim_result(met | missed | not_directional | unknown)
  reference_date / reference_value / observed_date / observed_value
  asset_return / benchmark_return / excess_return / alternative_return
  max_adverse / max_favorable / note / computed_at

Review              # 只追加，引用同一条目的结算
  review_id / entry_id / settlement_id
  process_class(sound_process_favorable | sound_process_unfavorable | flawed_process_favorable | flawed_process_unfavorable | undetermined)
  lessons / evidence_refs / recorded_at
```

与草案的差异：

1. 结算状态去掉 `pending`：未到期的检查点不写记录，由结算运行时计算。
2. 引用价拆成参考日与参考值，并记录实际观察日，便于核对非交易日、停牌和退市。
3. 复盘的过程分类采用“过程是否合理 × 结果是否有利”的四象限加“无法判定”。

结算规则分两类：`price_relative`（标的相对基准与替代，本阶段实现）和 `metric_observation`（宏观、市场、行业指标，本阶段登记为 `not_settleable` 并说明需要阶段 5 的数据）。

### 4. 路由与配方

```text
RecipeDefinition
  recipe_id / question_ids / title
  handles           # RecipeMatch(subject_type, intents 完整集合, personalization 允许值)
  steps             # RecipeStep(step_id, description, system_module, status(available | partial | planned),
                    #   produces 元素, roadmap_stage, entry 公共入口, decision_lane, personal_only, counter_evidence)
  output_elements   # 与长期愿景“必须包含”逐字一致
  avoid_checks      # 与“必须避免”逐字一致，可结构化检查的写明 enforced_by
  required_user_context / optional_user_context / supported_depths / sub_recipes

RoutingResult
  request / status(executable | partial | gap_only | needs_user_context | unresolved_subject | unresolved)
  recipe_ids / steps(含生效状态与说明) / coverage(元素状态) / gaps(元素、缺失系统模块、阶段)
  avoid_checks / user_questions / subjects(解析结果与候选) / suggestions

RecipeRunResult
  routing / status(executed | blocked | not_executed) / step_outcomes(步骤、状态、摘要、产物、下一步) / ledger_entry_ids
```

与草案的差异：配方增加“必须避免”检查项和可选用户上下文；路由结果增加元素覆盖；缺口按元素而非按步骤组织。
